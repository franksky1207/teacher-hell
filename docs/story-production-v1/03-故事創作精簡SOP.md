# 《教師荒謬地獄》｜故事創作、AVG 接線與驗收主流程

> **唯一操作入口**。新 T／G 故事的構思、正式稿、AVG 演出、故事匯出及核准都按本檔順序執行；既有故事只補演出時，從「既有稿入口」開始。**同一 ID、同一 Markdown、同一真相來源**；不建立平行 AVG 故事稿。本文件取代舊版「十步創作＋六步演出」的雙流程敘述，章節位置不再具有規格意義。

### A. 先規劃，再占用固定故事身份

1. **先認定故事類型**：T 必須真正依附指定校曆或制度節點；G 可跨時間成立；P 是另一套被動事件格式，不走 T/G 2400 種子與四選八 R；H4 另依畢典後程序。對 T 查唯一定案日期表與合法前／後共用池；同日跨 T 主題創作配額共用六篇，配額日不等於唯一播放日。
2. 先看已分配種子與本篇人物配置（含必要的 E 欄備註），不要自行更動已預選 ID、種子或人物事實。先對照既有及同池故事摘要，找出真正不重複的教師困境；**角色換名、場景換裝不算新故事**。
3. 四欄摘要固定：事件起因、核心衝突、導師困境、故事獨特性。T 須額外寫清楚「離開該時段就不成立」的理由。T 整池共同規劃放本池唯一的 `故事主題與摘要規劃.md`；不增平行企劃資料夾。


### 現代生活真實性：所有 T／G 故事的強制創作檢查

**以故事實際發生的年月、地點與人物生活條件為準**，而不是以作者或 AI 的舊印象、單一世代刻板印象或現實當日時間為準。本作從 2026 年起的臺灣高中校園情境，應在各方面符合當時合理的日常生活；未來學期只可依已確定的遊戲設定與可查證事實推進，不能憑空宣布未來新制度、軟體普及或科技能力。

1. **通訊、人際與跨國聯絡**：同儕、家長與跨校私人往來優先考慮符合人物習慣的手機通訊、LINE、Instagram 私訊、社群／班級群組、簡訊或通話；但不要假定每人都有同款手機、相同 App、帳號、網路或願意加好友。公文、學校承辦、正式活動聯繫可以使用電子郵件、校務系統及正式通知。手寫信、實體卡片、電話及面談仍可出現，但須有**具體情境理由**（例如紀念、個人偏好、特殊限制），不可機械地把高中生的即時聯絡一律寫成「寄信／回信／寄地址」。沒有交換帳號或取得同意，不得憑空變成能私訊對方。
2. **數位工具與資訊傳播**：寫出現實中常見的拍照、群組轉傳、截圖、雲端文件、搜尋、翻譯、生成式 AI、學習平台、行動支付等時，須符合當時普及程度、實際可用功能、校規及設備限制；不能把 AI 回答當已查證事實、把截圖當正式公告、把已讀／上線當有義務秒回，或假設科技百分之百準確。
3. **學校教學與行政**：依遊戲校曆、臺灣高中實際作息、班級經營與學校核定規範寫出合理的作業、段考、學習歷程、家長聯絡、請假、活動分工與評量；不可套用過時的教學程序、虛構官方規定或讓導師越權替科任、行政、校外人士承諾。
4. **消費、交通、空間與家庭生活**：購物、付款、寄送、交通、休閒、家庭與打工等細節須符合故事所在地和年代；避免把過時設備、流程、物價或生活方式當成每人預設，也不要把有無手機、信用卡、社群或經濟資源寫成品格高低。
5. **口語、流行文化與社會互動**：使用符合臺灣當代高中生、教師與家長身分的自然繁體中文及臺灣用詞；不硬塞網路流行語，也不把所有角色寫成同一種口吻。人物對隱私、同意、性別、家庭型態、跨文化禮節、界線與公共發言的理解，應合理反映時代及個人差異，不以刻板印象取代具體情節。
6. **制度、法律與未來時間**：學生個資、影像與錄音、帳號、網路公開、跨國聯絡、校園安全及權責均須核實合法性；「現在常見」不等於「每個人都能／應該用」。有年份差異、地方差異或尚未證實的流行習慣，先查證或改寫為不依賴未知資訊的情節，禁止捏造未來公告。
7. **不得反向機械替換**：現代化不是全面刪除紙本、書信、現金、面對面談話；若特殊情境合理就保留。修稿只處理確實違和的媒介、程序、語氣及因果，並檢查改動會否影響權限、資訊先後、四個已完成教師行動與八 R 客觀後果。故事原文及 AVG 必須同步更新。

**落地方式**：在 A 規劃時寫下故事年份、場域、實際媒介及可用性；B 創作逐頁自然性自查；C 按 05 的現代情境驗收表逐篇檢核；D／E 確認對話框的 chat／phone／現場演出與媒介一致。修正不合理細節後依影響範圍重驗，不為了一個用詞重跑無關大型測試。

### A-補充｜共用池先建立「可播放日期清單」，再寫故事（強制）

1. 從 [T20 唯一日期表](../T1-T6-特定故事20主題與觸發日期.md) 讀取本篇 `required_window` 對應的**全部**合法日期及前／後池階段；`quota_date` 只用於六篇創作配額。不得自己重算日期或把不同池合併。
2. 寫標題與四欄摘要時，逐一假設該篇抽到池內**每一個**合法日，檢查前／後事件是否已發生、剩餘天數、可能隔週／假日、人物在場與已知事實。不成立就先改題材敘述或補上正式可驗證資格，**不准帶著時間矛盾進第 4～5 區**。
3. 出現「第一天、最後一天、明天比賽、明天上課、昨天才、倒數一天、只剩幾天、下週一」等，必須依上下文辨識是否暗示某個限定日期；**禁語搜尋只找候選，不能替代逐日語意審查**。事件內自然跨時的「隔天」不必機械刪除，但不得預設跨假日／考試／活動的下一個日曆日仍有課。
4. 不得把只能發生在池內某一天的情節用模糊字替換掩蓋：若核心機制只有該日才成立，須按 02 回頭處理合法播放資格，不能維持共用池卻把限定日劇情當通用故事。

### B. 原稿創作：真正的先後關係

1. **角色合法性**：依 01 確認每個常駐持碼者的實際身份、在籍、職權、知情與四碼持有資格。無數值臨時背景人物可說話，但不建常駐 ID／數值／跨篇記憶；不要因為想要同框兩人就硬新增常駐角色。玩家始終是導師，不能擅自接管別科任課教師的課程、評量或教學。
2. **四個教師行動**：先自然產生 1 個情緒候選＋6 個實質不同、合法的普通候選；去重後**實際隨機取 3 個**，再把共 4 個行動實際隨機安排 A～D。只有 1 個 `emotional=true`，其餘 3 個為 false。每個行動都必須寫清**教師已完成的客觀行動**與利弊；情緒選項不是故意設計的錯誤答案。候選、抽中編號與最後映射只留在審查紀錄，不塞進五區塊。
3. **先排教師 V3 四狀態**（精神、熱忱、情緒、掌控）：依 05 的 A～E 合法組別，不重複抽四組、先排合法 8×4 增減，再反向創作支持數值的八個共用 R。每 R 最多兩個 0，各欄總和 −4（均值 −0.5）；這是教師四狀態，**與 NPC 每碼單 R ±8 的限制不同**，NPC 八 R 均值 ±3 已取消。任何非零增減都要能指出當事人的實際反應。
4. **八個共用結果**：R1～R8 各有不同客觀轉折、人物自主反應及合理收束，不能把 A～D 寫成四套 R。結果不能替玩家**追加只有某一選項才會做的教師行動**，更不能取消已完成的選項事實；未知事件不可當已發生。避免『發生一件事→老師提醒→宣告原則』的固定套版。**開場優先以接近 140 字、每個 R 優先以接近 130 字構思完整事件，再按實際需要增減**；110 字（開場）與 90 字（結局）僅是一般參考範圍的起點，絕不可當量產寫作目標。**不重複敘述、人物對話優先、情節完整**三項並列最高原則；開場與 R 的字數級距及唯一計數方法集中依 05，不在本檔複製另一套。開場依情節自然分頁，不強制補字。
5. **再排 4×8 因果權重**：依 05 **先列 32 格相容性／促進或抑制／理由，再填 4、2、1、0**。0 只能是客觀互斥，每列最多 2 個、每欄最多 1 個；4/2/1 必須有具體促進、中性或抑制依據。相對權重不代表好壞或固定機率；沒有必要製造 0。原 R 的故事事實一旦實質修改，**全 32 格重判因果**，原來合理的權重可不改。
6. 依 04 格式完成五區塊；依實際階段使用 `summary`、`choices` 或 `full`，完稿後可直接驗 `full`，不必重跑前期階段；第一次核准記錄六選三、NPC 因果、32 格證據、標籤實質核對及摘要／全文重複性。不得聲稱工具能推斷「故事好看、人物真的知情或 32 格真合理」。

### C. 原稿內容驗收關卡

依 05 七項實質審查：故事與角色、四碼、四選項、八 R、32 格、時間／法律及查重。每個 R 都要檢查完整度與八種結果的實質差異，以及開場／結果是否有重複敘述、空泛旁白或人物本可自然對話卻被代述；每批按 05 的唯一計數法自動統計開場與 R 字數、短結果及前後縮水警示，防止量產後段縮水。發現不足須**直接局部修稿→重判受影響因果／數值→同步 AVG→複驗**，不為達到平均字數灌水。內容尚未核准，不能當穩定的 AVG 量產基準。

### D. AVG 腳本：開場與八結果都要真正像戲

**AVG 接線不補字**：先辨識真正要呈現給玩家的正文，再計字；創作與檢查時僅台詞／訊息／必要旁白的正文計字；`{{...}}`、`enter`／`exit`、`speaker`、`expression`／`pose`、`scene`／`music`、`presentation`、P／R 標記與 JSON 格式**全部 0 字**。完整清單與唯一計數法以 05 為準；不得把人物進退場及任何接線欄位當成故事內容。

**演出最高準則：人物對話為主，旁白能不用就不用。** 優先讓實際在場的人物用符合自身口吻與知情範圍的台詞推進事件；遠端家長用通訊或電話介面。旁白只限真正需要的場景交代、客觀轉場、無法由角色自然說出的資訊。**禁止只把第三人稱敘述改標speaker，或為了湊對話讓角色朗讀旁白。** 每一頁的對話須有新增資訊、反應、轉折或收束；**上一頁已演出的事不可換句話重複，台詞說清楚後不可再加旁白複述**；不能為了湊到開場 140 字或結局 130 字灌水。不強迫每頁都有對話，必要旁白仍可保留。


1. **先拆故事事實，再寫演出台詞**：讀取四欄摘要、開場 P、四行動、八 R 原文及每位人物能知道的資訊。把 R 拆成可表現的行為、人物真正說出口的台詞與必要敘述。角色對話框不能唸「他表示」「你接著」「某某看見」等第三人稱總結；這些屬旁白或對應特殊介面。不要強迫每個 R 固定三頁，必要時二到多頁。
2. **每個 R 使用 `results.Rn.pages`**：非空陣列，每頁有非空 `text`，其餘合法欄位依 04。新作應依內容自然拆頁，對話／旁白／遠端訊息各用適當介面。**純演出改編**可將第五區敘述轉成等義的角色台詞，但每項客觀事實、知情與行動都必須一一對上；**直接分頁重現正文**時，R 原稿合併文字與 AVG 分頁文字須一致（忽略分頁空白）。若第五區敘事本身補強或修訂，必須同步更新 AVG 並重審受影響因果，不能只改其中一邊。
3. **鏡頭就是劇情的一部分**：每頁要問「現在在哪裡、誰真的在場、主要描寫誰、誰在說話、誰離開／進來」。**角色退場後若要再次現場發言或動作，須有合理重新登場；旁白僅提及遠端／不在場人物則不強制出場。**人物、表情、成人姿勢與背景須自然一致；一幕最多兩位 NPC。旁白轉到學生 B 的行動時，通常應切換到 B 的立繪；但單純提到遠端家長，不代表家長在教室登場。電話／通訊的遠端人物以 `phone`／`chat` 呈現，不硬加現場剪影。轉場前必要時先 `exit` 再 `enter`。
4. **八 R 相互隔離**：每個 R 獨立從同一開場結束狀態進入；R 內依序保存場景、人物與表情，切換 R 須回到新結果的第一頁；不能從前一個 R 帶過人物、對話或情緒。
5. **一篇一首背景配樂**：從合法 `school`、`conflict`、`serious`、`home`、`playful`、`touching`、`absurd` 選一首，設在整篇故事，不能按頁或 R 換曲。人物衣著依校曆情境與既有美工規則；不因台詞自行生成新美術。
6. **同時反向對照原文**：逐 R 逐頁查新增承諾、時間倒序、角色知情不合理、教師權責被擴大、事件被提前完成、學生反應被誤寫等。演出是轉換而不是重新創作。範例可參照 `T1-001～005` 的已製作腳本及 `驗收紀錄/T1-001-005-AVG第三階段內容因果驗收.md`，**但範例不是固定頁數、固定角色數或免驗收憑證**。

### E. 先自主驗證，再把成果交給使用者

- **資料層**：全 P 頁、全部八 R、分頁數與非空文字、合法欄位／場景／表情／姿勢、登場退場及各 R 隔離。特別確認**`avg` JSON 必須置於 `### 開場` 之前，不能出現在任何玩家可見 P 頁**；匯出後正文不得露出 `avg`、JSON 欄位或 Markdown 程式區塊。直接分頁轉寫須逐 R 核對原稿／AVG 文字；台詞改編則逐事實核對。先跑相關 Node 定向測試，不為單篇重跑三年模擬。
- **內容層**：按本批實際篇數 × 8 列出結果清單，**逐 R** 對照原始事件、客觀後果、既成選項行動、人物知情與 32 格前提；不能用少數抽查代替全批文字驗收。**不是只檢查台詞裡出現人物姓名**；旁白的主要人物、動作、場景都要對上。一般 4×8 任一 R 在合法非零權重選項下不應產生硬矛盾。只補演出時先確認第 5 區全文與基準版逐字一致。
- **修正迴圈**：同批問題集中修正，只重檢受影響的內容與資料；原 R 的事實或必要前提變動須重判全 32 格，純 AVG 表現調整則只檢查受影響頁面及資料。不因小錯誤重跑無關測試，也不以抽樣取代全部 R 的內容審查。

### F. 版本一致與發布

```text
來源分支 Markdown → scripts/export-story-reader.mjs
→ Publish story reader（gh-pages/stories/data/index.json＋stories/<ID>.json）
→ 索引與每篇 sourceCommit/sourceBranch 必須相同
→ 匯出資料的 P 開場與 R1～R8 內容完整，版本一致
```

- 生成 JSON 只能由發布流程管理；不得直接改 `gh-pages/stories/data` 充當來源修復。每個故事 JSON 與索引均須有發行版本，測試中心須核對一致，更新窗口不一致則重讀，持續失敗則**明確拒絕舊資料**。
- **Actions 綠燈不等於內容核准**：分別記錄來源提交、故事匯出、發布來源版本與劇情語意驗收。
- 每次部署只做相關工作流程及最小定向驗證；同樣的證據不重複跑無關 CI。必要時先用已匯出的 JSON 做編譯驗證，再確認公開版本。

### G. 批次封關與正式交付

1. **一批一次施工與自驗**：按使用者指定篇數完整施工，再整批檢查、局部修正並複驗。優先使用十篇一組的品質統計觀察前後變化；批次大小由任務與劇情複雜度決定，不再保留已過期的 T1-006～010『首次驗證』指令，也不為追求篇數跳過逐篇檢查。
2. 每批記錄：故事 ID／範圍與 SHA、R 數／總頁數、開場與八 R 字數分布、短 R 警示、是否有後段縮水或敘事套版；文字與 AVG 逐 R 對應方式（逐字／語意改編）、原第五區是否修改及 32 格複核；人物／場景／遠端演出、定向測試、公開 Pages 來源版本、修正及待辦。驗收文件就近放各主題的 `驗收紀錄/`，**不可混入故事池供讀取器誤掃**。
3. 完成狀態分開寫：**原稿核准／AVG 腳本完成／定向編譯通過／內容因果通過／已發布且同版本／正式遊戲整合**。前項成立**不自動**代表後項成立。
4. 任何形式的驗收都不省略 GPT 的劇情與 AVG 場景、人物合理性判斷；同時不要把機械驗證反覆跑到浪費 CI。正式跨主題、T648/G1752 與遊戲引擎全接線是後續另有關卡的工作。

```bash

npm run content:draft-check -- --input work/your-story.md --stage summary
npm run content:draft-check -- --input work/your-story.md --stage choices

npm run content:production -- status
npm run content:production -- windows T1-1
npm run content:production -- duplicates T1-001
npm run content:production -- audit T1-001

```

**驗證節制**：同一 Git SHA、相同輸入與檢查範圍已成功的結果不重跑；改稿只重驗受影響範圍。`audit --evidence` 使用實際對應稿件的證據，不得捏造六選三歷程；CLI／Actions 未執行須照實記錄。

## 四、暫存分支、定向驗證與整批交付

本節是提交及測試的**唯一執行規則**；故事合格門檻與正式證據欄位依 05，不在此重複定義。只改內容或 AVG 資料的工作，不因為曾有個別系統事故就固定追加播放器、瀏覽器、全遊戲回歸測試。

1. **先隔離，再完成整批**：核對正式 `content/events-production-v1` 的基準 SHA，在 `work/...` 暫存分支完成指定篇數、全部 R、AVG、人物與數值、32 格及審查證據。草稿期間不建立 PR（Draft 也可能觸發 CI），不逐篇推送正式 V1，也不碰 `main`。
2. **完整內容一次審查**：每篇依 05 核對七項品質、各合法日期、所有八 R、32 格具體因果、選項及數值；整批完成後集中檢查主題重複、前後稿件品質與字數警示。原稿和 AVG 同一事實、同一最新 SHA，不因格式通過就宣稱劇情合格。
3. **按修改範圍做定向驗證**：優先在可用的本機 Node 環境使用 `full`／`audit --evidence`、必要 JSON 與 AVG 資料回歸。已驗證且輸入與程式未變的相同項目不重跑；只改 AVG 立繪、表情或旁白但未改故事事實時，不重抽 V3 或重審不受影響的 32 格；原始 R 事實／必要前提變動，必須重判全部 32 格並同步演出和證據。
4. **環境不足如實列待驗**：無法使用完整 Node 專案時，先做可用的唯讀及內容審查，列出未執行命令和原因。不得提前開 PR 借 Actions 除錯，不得冒稱未執行的項目通過。
5. **必要時才使用 PR／Actions**：只有使用者授權進入正式晉升階段、且整批品質與可用本機檢查已完成，才評估一次 PR 與必要 CI；PR 是否 Draft 均先查實際 workflow 觸發範圍及本批故事／evidence 涵蓋。Node 環境受限時可由必要 Actions 補做同等的定向驗證；真錯修復後僅重驗受影響項目，不重跑無關流程。
6. **正式晉升後核對版本**：獲授權後一次更新正式 V1，核對 `stories/data/index.json`、單篇 JSON、`release.json` 的來源 SHA 及 P／R1～R8 資料完整性。僅有本批暫存稿或驗收報告時，不進行發布，也不把 S5 說成已完成。
7. **一批一份可追溯報告**：依 05 現有證據 schema 保存逐篇實際審查資料，批次報告只彙總通過數、警示、具體修正、必要命令及結果、分支 SHA 與未驗事項；不把每一格已存的長篇理由再全文複製一次。報告更新不觸發不必要的正式發布。禁止虛構隨機抽選、人工審查或 CI 執行歷程。

**交付準則**：創作中的暫存分支只回報已實際完成的 S1～S4；正式發布與版本核對達成後才記 S5，另經授權正式遊戲整合才記 S6。不得以減少證據文字取代實際語意判斷，也不以「只跑一次」為由放棄修正真正的錯誤。
