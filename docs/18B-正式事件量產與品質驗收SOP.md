# 第18-B｜正式事件量產 SOP

> **現行唯一事件量產流程｜2026-11-16。** 適用 T01～T16。目的是製作具有真實因果、數值作用與文字魅力的臺灣私立高中導師遊戲事件，**不是累積檢查項目**。本文件取代同檔先前冗長的12節與過時進度說明；歷史審查與PR紀錄不再充當規則。數值公式與引擎契約本次**不修訂**。

> **T04 起採小主題完整製作、內部可恢復保存點**：ChatGPT 一次受領一個小主題的完整創作、審查與修正任務；工具呼叫及 GitHub 保存可按實際負擔分段，不必請使用者反覆下「繼續」。細節見 [18B-串流中斷與恢復執行規範](18B-串流中斷與恢復執行規範.md)。**不改創作、審查、數量或發布門檻。**

## 一、四項核心原則

1. **世界可信**：事件發生的時間、人物身分、教師權責、知情來源及校園制度，必須符合當下遊戲世界。誰做了什麼、誰知道什麼、什麼尚未證實，不能混淆；必要安全與法定程序不受選項或亂數任意取消。
2. **因果成立**：選項必須代表不同且可行的教師行動；結果由實際行動、既有事實、人物與環境條件推導。未發生的事情不能寫成已完成，未在場者不能自動知情；跨日、長期問題、關係變動及多結果**需要才使用**，不能為增加複雜度而硬加。
3. **數值有據**：事件抽選、人物反應、策略成效及世界變化都應讀取適當的既有數值／歷史，依其定義、持有者和公式運作。數值代表機率傾向，不是保證成功或固定失敗；效果發生才合理更新，不能為填滿欄位亂加減、將同一效果重複結算或把長期能力當短期情緒。**48數值、N1～N8、K倍率、六能力與各項公式仍以現行正式來源為準；待另案討論，不在事件稿中暗改。**
4. **文字有生命**：人物說話、情緒、細節與幽默要服務於個性、情境及玩家體驗；不同事件應有實質不同的起因、責任或發展，不得只靠換姓名、背景或措辭灌數。細節可以不改數值，但必須有敘事意義。保留溫馨、普通、荒謬、衝突與困境的自然多樣性，不設固定情緒或分支配額。

**使用方法**：先問細節是否服務上述核心，然後才判斷所需的引擎功能。不是每件故事都要有加權分歧、跨日、多人、歷史碼或數值變化；有使用時必須真正成立。

## 二、數值、資料與技術權威

本 SOP 只決定**使用原則**，不複製數值表或重訂公式，以免出現多份互相矛盾的規格。

- **數值定義與計算**：以既有 `docs/02` 數值文件、N1～N8正式公式及執行中的數值模型為權威；候選六碼、權重、方向、來源、valence與合法持有者依正式契約。數值能否讀取或改變，應由實際持有者及編譯／驗證結果判斷，不能只檢查代碼格式。
- **事件與遊戲世界契約**：以 [17-D事件內容製作契約](17D-事件內容量產SOP.md)、現行 `validateStory`、`validateEventDefinitions`、`compileStory`、正式交易、行事曆與場景資源為權威；四個基本選項、必要情緒選項、條件替換及版本管理依既有引擎，不另建平行結算器。
- **已知／說法／歷史／問題根**：使用現行 `outcome.world`、`claims`與傳達、`historyCodes`、`relationshipChanges`、`issueOperations`、`eligibility.issue` 等**現有合法功能**。歷史分類不是持續問題狀態；沒有實際接觸或可得證據就不能傳播知情、調整關係或聲稱問題已解決。
- **資料一致性**：作者原始稿為工作來源，遊戲 JS 按現有同步程序生成；內容、定義、版本和審稿證據一致，舊版已引用的資源不能悄悄替換。工具參照 [18-A檢查器規範](18A-事件量產工具使用規範.md)。
- **模型缺口**：若合理故事無法由現有數值或介面表達，先記錄「實際需求、現有侷限與影響」，而非強塞不相干欄位。48數值及公式等另案討論，不因單篇草稿自動變更。

## 三、一次完成的產製與驗收流程

**① 探索與撰寫（首輪抓30件）**：每個小主題**首輪必須以30件真正不同、具備完整事件內容的獨立故事為製作基準**，不是只有30個標題／情境候選，也不是寫到20件就停。30是起始製作量，不是上限；若還有值得採用且實質不同的題材，可以超過30件。經審查、修正與必要淘汰後，**每小主題最終正式品質核可數不得少於20件**（16大主題×8小主題，正式最低2,560件）。先比較既有已接受稿，決定客觀起因、玩家能做的不同策略、可能的合理結果，再寫人物與細節，並選用適當的數值和因果功能。**一個小主題就是一次完整製作任務，必須包含首輪30件撰寫及其後審查、必要補量**；內部的探索、撰寫、即時自檢與 GitHub 保存點不算新的正式批次，也不強制按 4～6 件拆分。可在同一使用者指令下接續完成，毋須逐件或每個保存點再下指令。

**② 製作時即時自檢**：作者寫作時順手檢查四項核心與合法契約；能由程式確定的結構、持有者、分歧因果、資料同步等問題，**在該稿產出時就修正**，不要等整批結束才發現系統性錯誤。輕量檢查不等於每小單元重跑全部測試。

**③ 主控內容審查（必要）／外部獨立審稿（由使用者選擇）**：由主控 ChatGPT 依四項核心、現行故事、已知審查與修正紀錄以及實際工程驗收判斷是否通過；作者自檢、ChatGPT覆核均可作為內容放行依據，不必另請其他AI。**只有使用者主動決定時**才交 Gemini／其他模型／人工做加強性的獨立審稿。已有外部審查紀錄可以參考，但不可把「缺外部簽核」列為阻斷。僅針對具體不合理之處要求修改或隔離，勿為了有審查紀錄而重做整批。

**④ 集中局部修正、淘汰、補量與結案**：審查可隔離或淘汰品質不足、因果重複、無法合理修復的事件，不為了保住30件而放水；先修真正能修好的故事，**再統計實際通過品質審查且達工程放行條件的獨立事件數**。若淘汰／隔離後剩餘**不足20件**，本小主題不得結案，必須另找實質不同的新題材，將**當輪有效候選製作池補回至少30件完整故事（包含保留通過者，不以已淘汰稿湊數）**，再審查新增或改動部分；如此循環直到有**至少20件實際通過**。若剩餘20～29件真正通過，允許結案，不強迫為湊30再增加劣質內容；若通過30件以上，也全部保留，不限制上限。只修阻斷事件及其真正受影響的引用；再確認對應版本與受影響契約，**不重新啟動全批創作或全批審稿**。已核可且未改動的事件不重審；若錯誤尚未解決，如實列待修／不放行，不為了結案假裝通過。昂貴執行期測試僅按風險選代表案例（通常最多三組），不跑三年／30年、全遊戲或大量seed。最後一次報告已完成／通過／未驗、修稿數、正式可計件數與來源提交，結案轉下一主題。

## 四、放行界線

- **作者完成 ≠ 結構合法 ≠ 內容通過 ≠ 玩家可抽到**。沿用正式 `authored → structurallyValid → reviewed → resolverReady → catalogueReady → publishedInNewCareers` 狀態；其中 `reviewed` 指**主控內容審查通過**（可以由 ChatGPT 自行審查），絕不解釋為「已由外部AI獨立簽核」。必要工程檢查須有對應版本的通過證據；外部獨立審稿是使用者自選額外品質工具，**不是放行門檻**。通過內容與工程門檻仍不等於授權合併／部署。
- **真正阻斷**：違反四項核心造成的無效因果、錯誤知情／權責、數值或資料契約錯誤、必要安全程序問題，以及正式載入／重玩／候選不能正確執行。修正應針對受影響範圍，不為非重大風格偏好重新開批。
- 原有八件獨立示範簽核、各主題審查證據與GitHub提交歷史保留供參考，不因沒有其他獨立簽核阻擋任一事件放行。草稿及 `engineering-test` 不計正式2,560件；未經使用者明確授權，不合併、部署、升 `ready` 或發布。

**執行準則：核心規則優先，細節必須有依據；數值要真的取用並影響合理機率，創作不為檢查而套模板，驗收只修真正有問題的地方。**
