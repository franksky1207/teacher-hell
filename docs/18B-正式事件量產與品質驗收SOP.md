# 第18-B｜正式事件量產與品質驗收 SOP

> **狀態：2026-11-15 修訂版；適用第18批試產及後續量產。** 本文件整合原「18-B 正式事件量產工作流程」及 T10-03 第一次試產發現的問題。這是**批次製作、品質審查與放行規則**，不是新事件引擎。每則事件的資料契約與細節仍以 [17-D 正式小事件製作與驗收 SOP](17D-事件內容量產SOP.md) 為準；自動檢查的操作以 [18-A 事件量產工具規範](18A-事件量產工具使用規範.md) 為準。與兩者衝突時，先查現行引擎並提出具體衝突，不擅自修改核心規則。

## 一、目標與不可變原則

- 正式庫為 **128 主題 × 每主題至少20則真正不同的小事件（基本至少2,560則）**，**20是下限，不設上限**。同故事不同選項、variants、換人名、日期或布景都不能額外計件。
- **最高原則：同事件、同選項仍可因已知人物特質、歷史、關係、教師狀態及合法權重，出現多個合理而且可追溯的結果。** 不可變成「選A固定成功／選B固定失敗」；也不可為了隨機而任意反轉。部分簡單選項可以只有單一結果，不能強制每個選項都塞多結果。
- 臺灣高中真實作息、制度與公開資料用來研究題材與權責，劇情人物與事件自行虛構；**未經查證的指控不得寫成遊戲中的既成事實**。一般日常、正向、荒謬、負面、長期困境都可自然存在，不設各類固定配額。
- 嚴守現有 17-D 四選項、自然情緒選項、資格替換、合法畫面、知情邊界、歷史與後續契約；不更動 N1～N8、K、事件配額、年資難度、校曆、存檔、曝光或事件引擎，不建立平行結算器。
- 40位學生需要公平的**實質互動機會**，不是強制輪流登場，更不能以危機灌曝光。試產內容預設**不進正式池**，未經明確放行不轉成 ready 或正式上架。

## 二、先骨架、再劇情的七個步驟

以下是**同一批的工作順序**，不是每個步驟都要獨立PR、跑大型驗收或等待使用者批准。

1. **選主題及查找題材**：讀取 GitHub 最新 T 主題、17-D、現有已接受事件登記簿；參考臺灣學校情境、法規與可核對的研究。標明來源、推論、虛構。不要為測試而虛稱資料出自新聞。
2. **建立事件骨架清單，先期去重**：每個候選記錄主題碼、暫定ID、客觀起因、教師實際職責、已知／未知與知情來源、人物與時段資格、主要策略、可成立的後果、**結果留下的事實／合理數值效果，以及該事件是普通結束、回應既有問題或建立／推進持續問題**，並記錄和同／跨主題已接受事件的**實質差異**。骨架相同先合併或改寫，**未通過骨架去重不可直接展開成大量正式劇情**。除起因外，還要比較**四個選項的實際策略與產生的結果**；僅改起因但仍是同一組四選項、同一條後果，也應列為疑似換皮。
3. **獨立設計因果與人物差異**：先依故事個別決定可見資訊、當事人動機是否仍未知、四種實質不同且合法的導師策略、哪些結果受關係／歷史／能力／不確定性影響。**先決定客觀結果及誰受影響、誰知情，再判斷數值是否值得變動；不強迫每次事件都有數值增減。** 若跨主題共享持續問題，必須能指出具體已發生的前因與合法狀態來源，不得只因同一學生、同類歷史碼或相近時間便宣稱因果。使用既有 `variants`、合法權重與必要的 `requires`，避免固定機率套版。分支後果要**實際不同**，僅換文字不算不同結果。**人物條件必須有故事內可理解的作用**：依當事人的既有性格、立場、信任、衝突或實際歷史，決定哪些台詞、資訊、可行策略或結果真的會改變；不是替40位學生套相同對話、只換座號和姓名，也不能憑空宣稱曾經發生未記錄的過往。不是每則日常都要用人物條件，必要時才依既有資料契約引入。
4. **寫成正式資料**：依17-D填入逐頁臺灣校園文字、可觀察反應、合法場景、四選項、數值／事實／主張／歷史／後續，並與候選定義一致。**安全、衛生及隱私的不可省略底線應在提供選項前先成立**（例如危險區域先隔離、清潔劑造成不適先停止使用、可能遭汙染的食物先停止食用、可能公開個資先停止散布）；玩家選的是完成必要處置後的不同合理處理策略，不應靠選中某一格才能避免顯而易見的傷害。只對實際需要的故事設定共同處置，不為普通日常強加危機。**劇情長短、角色數、場景、節奏及是否跨日由事件內容決定**；不得所有事件都強制兩頁、同四策略、同單階段或同結局。單純日常也不必硬寫多階段。**跨日後續不得假設玩家曾選某一選項或已獲某一加權結果**：先列出每條前日分支均確定成立的共同事實；若隔日對話必須依不同結果改變，應使用既有合法事實／歷史紀錄及條件機制銜接，不能靠沒有持久記錄的敘事臆測，也不能為了表現連續性而強迫每則跨日。
5. **精準結構檢查**：用既有 `validateStory`、`validateEventDefinitions` 與18-A檢查器驗結構、合法資格、版本、重複候選、多結果等價預警。工具字串相似度只是提示；**程式檢查通過不等於語意品質通過**。錯誤只修相關事件，必要時再做單一事件／核心相容測試。
6. **獨立AI劇情審查及修正**：由**不同於撰稿與自檢的獨立審稿流程**逐則審查真實感、已知事實與傳聞、臺灣制度及權限、四選項差異、同選項多結果因果、人物與時間、連鎖合理性、跨篇換皮。特別做**起因→對話→四選項→實際後果→跨日後續**的前後一致性檢查，並查核必要安全／隱私處置是否對所有選項路徑成立、是否有人物既有資訊／關係／歷史可證明其差異：不得在查證前認定別人有錯，也不得先說沒有姓名、後續卻在毫無查證下說確定有姓名。紀錄**具體ID、問題、修改、再審結果**，不得只填 `approved` 或一句空泛理由來冒充審查。校安、霸凌、性平、身心危機等需額外程序查核；審稿未完成即待審；**同一模型反覆自我修改可記為自檢與修正，不得宣稱已完成獨立審稿**。
7. **批次遊玩體驗審查及存檔**：對照累積內容，統計起因、教師策略、結果類型、人物／年級、正負基調、故事長短、單日／跨日、時段與場景的重複情形；注意連續玩法是否都像在選相同四句、是否所有結果只差一個數值。**不硬性配額，不以此取代第21批正式平衡與三難度驗證**。保存審查證據和下一批可比對的 baseline。

## 三、第一輪 T10-03 試產的失敗教訓（不得重犯）

- 首次 PR #60 測試資料有20個不同起因與四個選項，但大量使用相同兩頁、同場景、單階段、相似策略與結果模板。**格式看似整齊≠故事多元**。再測試時沿用20個已有骨架，**逐則決定真正必要的改動**，不為多階段而多階段、不整批重做。
- 先前測試先建立了測試案例，卻未拿到該 PR 最終專項 CI 的完成證據。**測試檔存在≠測試通過**。每次報告必須分清已寫、已執行、通過、失敗、未觸發、未驗證；CI沒有觸發時可使用可核對的等價精準命令，但沒有實際執行就明確註記未驗。
- 即使20則結構合法、具有 variants，也不能宣稱人物歷史、跨日後續、存讀與不同策略皆已測過；**覆蓋範圍須按實際案例逐項列出**。代表性多階段、人物條件與結果差異可在適合的事件中測試，不強迫所有事件使用同結構。
- 第一輪品質審查明確指出模板化，故 PR #60 **尚未通過完整語意／玩法品質驗收**；不得由 authored 20 直接推論正式庫完成20或已有20則可上架。

## 四、長期因果的先決審查與工程界線（2026-11-15）

本節統整17-D事件結果記憶規格及三學年長期因果研究。**第18-B批尚未獲得正式量產授權，暫緩繼續製作新事件及反覆跑舊20筆測試**；先確認故事所需共用問題狀態可從既有交易重建，必要時才提出小範圍接線。不得把研究構想寫成已實作的功能。

- **結果與歷史分層**：每件事件結果至少有可追溯客觀事實；`changes`可為空，不硬改長期人格／定向信任；`claims`僅是有來源的觀點；`historyCodes`是分類，不是「未解決／已解決」開關，舊事被後來引用不再重算數值。
- **問題狀態不複製**：優先由當前世界的既有事實、來源、人物、已確認結果與時效投影出「仍有效／已收束／已不適用」，保留可回查的來源事實；若缺少可辨識的承諾內容、履行證據等資訊，**判定為未知／資料契約不足，不得推測為已結案**。不因久未抽到故事就自動消除重大未解事項。
- **不同主題可共享問題**：跨事件可共同推進同一個明確問題，事件原身分與結果一次性結算仍分開；故事只在真正有前置關係時引用來源，不得把同人物、同標籤或先後次序等同因果。原本`direct/cumulative`資格、正式日型額度、K、冷卻及互斥保持。
- **三種人物集合分清**：當事人／受影響者／知情者均應有可追溯依據。跨人物定向關係及資訊傳播須檢查現有交易是否有合法接線；**不得直接往現有`outcome.changes`塞尚不支援的關係物件或新增未知故事欄位**。
- **收束、時效及畢業**：普通日常可當場結束；改善、惡化、沉寂及失去適用條件不是同義詞。已完成承諾須有履行的客觀事實；同學離班或畢業可能使在校相遇不適用，卻不會抹除其歷史。必要程序的合法時限另依既有校務流程，不能用事件抽選隨機性決定有無履行義務。
- **驗收改為少量跨事件代表案例**：只要代表性地證明「數值為零或有明確原因才更新」、「具體未履行承諾被另一主題合理引用且能收束」、「跨人物知情不洩漏」、「三學年中途可改善或自然結束」；不要求2,560個小事件都設跨年分支，也不為驗一個案例重跑三年遊戲。
- **工程待決點（不得視為完成）**：具體問題的唯一辨識與收束判定是否能完全從現有事實推導；一般故事對任意兩個NPC定向關係的寫入接線；複雜 AND／OR 及非`cumulative`事件的跨問題資格；大型歷史索引的效能。逐項提出最小必要修改、相容性及回退方案，確認後才實作。

**架構選擇原則（D項複核更新）**：允許新增必要的結構化問題操作、關係效果、候選問題綁定、可重建索引及實測後需要的檢查點；不以零新增欄位為目標。真正要避免的是缺乏單一權威來源的重複資料、無可追溯交易的額外數值與不必要的第二事件引擎。\n\n**放行決策**：引擎的單事件與跨日能力已有局部驗證，不等於長期問題網絡驗收。若仍缺合法問題狀態／知情／關係接線，標記「架構待補」，**不得靠增加T10-03測試次數或將測試稿改成`ready`來跳過**。

## 五、測試身份與放行門檻

**測試批：** 用 `engineering-test` 與 `engineering:` ID，留在隔離測試資料或非正式資源；不註冊進正式候選池、不得誤設 `ready`、不進玩家新生涯、不計正式上架。測試通過只是工作流程與樣本合格，**不代表自動轉正**。

**量產正式批：** 逐則保存主題、唯一資源／定義ID、版本、來源、骨架、狀態及必要候選資格。以資料狀態區分：
- `authored`：已撰稿（包含未完成／未審，不能當合格數）。
- `structurallyValid`：實際執行結構檢查通過。
- `reviewed`：具體AI語意審查紀錄已完成；這是審查紀錄，不代表絕對正確。
- `resolverReady`／`catalogueReady`：正式資源解析與目錄接線已驗證。
- `publishedInNewCareers`：另經真正新生涯合法抽選／接入證明，否則維持 `not-assessed`。

**可判定單主題試產驗收通過的最低條件：** 20則以上實質不同的起因；每則符合既有資料契約、基本四選項與合法結果；完成具體、可追溯的AI語意審查與跨篇去重；批次代表案例實際驗證加權多結果、人物條件（如適用）、長短或後續變化（如有）；必要精準測試有可核對結果；測試內容仍隔離且不宣稱正式上架。若有未完成項目，狀態只能是**需修正／未驗證**，不得整批宣告成功。

## 六、測試與 GitHub 成本規則

- 先執行**本批專項、單一事件／內容契約**檢查；錯誤定位後只修受影響的檔案與事件，重跑必要範圍。**不得為驗一批內容而反覆跑三年／30年模擬、完整瀏覽器矩陣或全部歷史回歸**。
- 不把 CI 未觸發當作通過，也不為了觸發 Actions 而任意調整正式分支。要驗證時，先確認 workflow 的觸發條件及目標分支；用既有精準命令或經確認的最小工作流程，明確回報證據。
- 每批回報：新增／修正事件數、語意退稿與具體修正數、可能重複清單、結構檢查執行結果、尚未覆蓋的功能、GitHub PR／分支、正式上架狀態。使用者不必逐篇驗收。
- 不自行合併、部署或將測試資料轉正。只有內容可驗證、技術驗證通過且經使用者授權時才做對應操作。
- ChatGPT 與 Codex 使用**相同規格與驗收條件**。先比較實際完成品質、修正次數、審稿成本與可查的用量再決定分工；不憑空宣稱哪一個比較省。Codex若用，只負責指定批次及精準修正，不自行擴張工作範圍。

## 七、跨批去重操作與限制

```bash
node scripts/audit-content.mjs --input work/new-batch.json --baseline work/previous-batches.json --output work/new-batch-report.json
```

- `--baseline` 使用**累積所有已接受事件**的靜態紀錄（陣列或 `{records:[...]}`），只做舊批對新批的疑似重複比對，不將舊批事件加進本批完成數；同批事件也互相比對。
- 字面不相似仍可能同質，AI須比對「成因、教師職責、資訊差異、四選項策略、後續因果」；有疑慮先標待審，不由相似度自動刪除。
- baseline不會由CLI自行下載 GitHub，也不會自行保證全庫內容完整；製作者要明確提供其來源與範圍。

## 八、A項設計契約｜具體問題的來源辨識、更新與自然收束（2026-11-15；規格提案，未實作）

**目的：** 讓同一件具體承諾、照顧安排、同儕衝突或行政未結事項，能被不同主題的事件在三學年內合法引用與收束；不新增平行世界交易、永久伏筆表或第49個數值。此節僅是待實作的資料契約提案，不得將以下名稱直接寫入現行正式故事 JSON：目前 `validateStory` 的 `outcome` 精確要求 `fact/claims/changes/historyCodes/next` 等欄位。

### A-1　資料權威與明確限制

- 唯一權威來源仍為正式世界 `facts`、`claims`、`disclosures/knowledge`、`history`、`commits` 及現有數值收據。**問題索引優先只讀、可重建；允許於原世界交易增補必要的結構化因果操作，也允許實測後採可驗證檢查點，但不得創造與權威事實分離且各自可修改的第二套問題狀態**。
- 現有 `fact.id` 與 `causeIds` 分別可提供穩定來源身分及合法因果前後關係；`Hxx-x` 僅是分類，`event-lifecycle:ended` 僅是事件實例結束，**兩者均不等於具體問題已解決**。
- 單靠目前的任意 `fact.description` 文字與一般 `causeIds`，不能可靠推斷是哪一件承諾或如何收束。需由**預寫內容明確聲明問題語意及來源根事實**，再由正式世界交易一次記錄；不可用文句關鍵字、LLM即時猜測、同角色／同主題標籤推斷。
- 世界存檔 `runtime.version=1`、邏輯 save v2 及前後快照有嚴格驗證；此提案**不直接改存檔外殼、runtime根欄位、N1～N8、抽選K或新事件額度**。若最終需擴充事實 `data` 的受檢語意，須確認舊事實可按「非長期問題」讀取而不遷移推測。

### A-2　最小結構化語意（欄位名稱暫定，實作前需再核定）

只對**確實有延續價值的事件結果**附帶可選的因果操作；普通午餐趣事、打掃及已完結日常不寫此操作。候選的作者語意可簡化為：

| 作者所需資料 | 意義與規則 |
|---|---|
| `operation` | `open`、`progress`、`close`、`invalidate`；這是**問題的語意操作**，不是現有 `event-lifecycle` 操作 |
| `rootFactId` | 同一具體問題的根源客觀事實。建立時以**本次結果提交後的事實 ID**作根；後續須引用已存在、較早且經核實的根 |
| `kind` | 預寫的具體問題類型／必要語意，例：承諾尚待履行、交通安排需協助。不可將單純 `H03-1` 當成問題類型與身分 |
| `actors` | 具體角色及其在該問題中的責任／受影響位置；必須綁定真實人物 ID，跨班／畢業仍沿用原 ID |
| `basisFactId` | 本次確認建立、推進或收束的客觀來源事實 ID；新變化須晚於根源，且引用合法因果證據 |
| `reason` | 收束或失效的可核對原因；例如已履行、當事人明確撤回、權責正式轉移。不得用「很久沒有出現」當已解決證據 |

以上**不是新的正式欄位清單**，而是作者／編譯器需表達的最小資訊。優先評估將已確認的語意**放在原有客觀事實的 `data`、隨正式交易提交**，以免永久重複存兩份問題狀態；但目前 `story.js` 產生的 `story-action` 事實 `data` 只含 `optionId/contentVersion/variantId` 等，沒有可編寫的問題操作。真正接入必須小幅擴充 `validateStory` 與 `compileStory` 的資料白名單及合法事實生成，不可直接由外部修改既有事實。

### A-3　生命週期：查詢結果與確定性

根事實存在而後續尚未有合法終止依據時，問題索引回傳**仍有效**；若有正式收束證據，回傳**已收束**；若時段／身份／校曆條件使特定互動不能再進行，回傳**目前不適用**但保留歷史；若來源資料不足或有互相衝突的證據，回傳**無法判定，不能強制結案**。

- `progress` 可留下新進展或惡化，但不應為已發生的舊後果再次加減數值。
- `close` 須有具體收束事實；同一問題重複 `close` 不得造成二次數值結算。
- `invalidate` 僅說明某項後續不再適用（例如已畢業且在校辦理的方案失去意義），**不代表家庭問題本身消失**。
- 已收束問題若之後因新事實再次成為困境，需明示**新問題**或有證據的**再啟動**規則；不得因一般數值波動自行重開舊承諾。
- **時間順序與證據**：根必先存在，後續引用的來源事實應較新；既有 `causeIds` 驗證只保證因果來源較早，並不保證被引用的問題根相同，因此問題關聯必須另有受驗的明確指定。
- **知情分離**：客觀問題存在不等於任何NPC或玩家知道。後續台詞／資格仍須符合原本 `disclosures/knowledge/claims` 來源約束，不能由只讀問題索引自動把真相洩漏給角色。

### A-4　最小查詢契約（只讀，可重建）

輸入：已驗證的 `world`、查詢所需人物／問題類型或 `rootFactId`、當前日期及角色知情範圍。

輸出：`rootFactId`、`kind`、`actors`、`status`（仍有效／已收束／目前不適用／無法判定）、`latestBasisFactId`、`evidenceFactIds`；**無資料應回空集合或無法判定，不可偽造已成立的根源事實**。這些為概念介面，不能當成現有函式或已能呼叫的 API。

- 查詢相同世界版本與同一套歷史，不會隨重整、讀檔或再次查詢產生不同結果，也不消耗亂數或變動數值。
- 由世界來源事實重建，索引的快取若有，最多作用於同一已驗證 world revision／單次查詢；不可跨存檔或失敗重玩沿用。
- 故事候選是否可讀此索引屬**C項資格接線**，本項只確保查詢有來源、可重播；不直接放入現有 `direct` 或 `cumulative` schema。

### A-5　最小驗收情境（設計案例，不執行測試）

1. **兩件承諾不混淆**：同一學生先後有「向家長說明」與「補交作品協助」兩個根源事實；完成前者不會把後者也標為已收束。
2. **跨主題推進與存讀**：高一出缺勤開問題、高二家庭聯絡以明確來源事實推進、高三確認改善並收束；存讀後問題狀態一致；中途正常結案亦合法。
3. **知情不自動擴散**：老師知情、同學不知情，同學不能在後續無來源地引用該問題。
4. **不強迫長期化**：一件普通午餐趣事在結果提交後自然結束；`historyCodes` 可空、`changes` 可空、不會產生持續問題。
5. **不因無後續自動收束**：半年沒有抽到相關事件，問題仍維持有證據的狀態；若人已離班，則在校觸發資格不適用，但原事件歷史不被刪除。

**A項階段判定：架構及作者語意可以定義；程式尚未實作、跨事件根引用與資料驗證尚未證實。** 這些規則不能取代既有18-B獨立語意審稿要求。B（定向關係）、C（候選資格）、D（索引效能）應以本項的根源事實及查詢語意為共同基礎，不能各自另造一套「目前問題狀態」。

## 九、B項設計契約｜跨人物定向關係的合法原子結算（2026-11-15；規格提案，未實作）

**設計立場：** 可新增真正必要的資料欄位；不以「零新增」為目標，但優先沿用已存在的N1～N8定向關係與正式世界結算，避免再建一套 `affection`／`trust` 隱藏數值。此項不修改目前 PR #60 事件內容與正式程式。

### B-1　實際已存在的能力與缺口

1. `src/world/relationships.js` 已有 `directedKey(fromId,toId)`、`createRelationship`，方向性 `5-1` 信任、`5-2` 親近、`5-3` 尊重、`5-4` 不滿四欄；A→B與B→A**不是同一條關係**。
2. `src/social/relations.js` 的 `relationshipView` 與 `prepareRelationshipChange` 可讀取、提出定向關係變更，但不是可供正式故事直接呼叫的世界交易。
3. `src/changes/targets.js` 的 `targetRecord` **已支援 `{kind:'relationship',id:directedKey(A,B)}`**；`src/changes/settlement.js` 的既有 `direct` 更新也能使用合法數值持有者與一次性收據。因此**不需新增底層關係數值類型或第二套結算公式**。
4. **真正缺口在正式故事內容端**：`src/runtime/story-content.js` 的 `outcome.changes` 目前只有 `role/holder/code/delta`，NPC以 `person` 為持有者；`src/runtime/story.js` 會將它映射成 `player-*`／`person` 的直接變更，尚無明確的**A→B關係效果語意**。
5. `src/runtime/transactions.js` 的 `fact.data.type==='contact'` 會依既有機制嘗試為合法接觸的角色建立關係；但建立關係**不等於已發生信任變化**。不能為了讓關係存在而偽造接觸，也不能假設所有未建立關係都可被故事直接改值。

### B-2　作者需要的最小擴充欄位（名稱暫定，並非現行有效 JSON）

建議在故事每一個**實際結果**中，允許可選的 `relationshipChanges` 陣列；與既有 `changes`（個人／教師數值）分開，避免讓 `holder` 同時代表人物和人物對人物。

| 屬性 | 應有意義／最小限制 |
|---|---|
| `fromRole` | **感受或評價發生改變的人**；先使用既有 `teacher/participant/companion` 角色綁定，禁止自由填未存在的姓名 |
| `toRole` | **被評價的對象**；先使用同一場正式事件已綁定的合法角色，兩者不可相同 |
| `code` | 僅 `5-1`／`5-2`／`5-3`／`5-4` |
| `delta` | 依既有數值效果範圍與N1～N8規則計算的有限變化；**可沒有關係變更，不要求每則一定出現** |
| `basis` | **本次已確認結果的事實 ID**，由編譯器在確認時合法生成／綁定；不能由文字作者猜測執行期ID |
| `reason`（編輯註記） | 哪位人物基於已發生、自己可觀察／可知的哪種結果改變態度；優先保留在作者審查／內容註記，不必另寫第二套永久因果史 |

以上是建議**最小作者語法**。若日後證實同一事件必須合理修改未在場的家長／同學，需再評估**明確人物ID、合法在場／知情／接觸來源及權責**；不能靠 `participant` 偷指其他人、也不能為了同時改全班評價而讓所有人憑空知情。

### B-3　唯一交易及來源驗證

- 正式編譯流程依 `fromRole/toRole` 找出已綁定的人物ID，以現有 `directedKey` 算出方向性的關係持有者ID，交原 `targetRecord(kind='relationship')` 驗證**該條關係與四欄數值確實存在**。關係不存在時先回報資格／接觸缺口，**不由數值變更函式暗中創建人物或關係**。
- 只在**玩家選項已確認且合法結果實際確定**後，與該選項其他個人數值效果一起編成原本單一 `result` 的 `direct` 變動清單、通過現有原子世界交易及數值收據；重新載入、重送或再次引用舊事實都不重新加減。
- 本次結果至少有可追溯 `fact.id`、事件ID、當事人及實際關係變動的數值收據；將變更的 `from/to` 由穩定ID及既有收據還原，不再建立一份新的關係變更歷史表。
- **不強迫左右對稱**：A→B改變時，B→A、其他同學C→A及群體風評不能在沒有獨立可成立後果時同步變動。同一選項可同時合法更新多條已存在的關係，但各條需有合理原因與去重規則。
- **不捏造知情**：`witnessIds`、主張及 `knowledge/disclosures` 仍依正式來源處理。角色自己在場看見某事，和角色日後才聽聞某個版本，對其態度影響可能不同；不能讓完全不知情者因世界真相存在就直接產生關係效果。若要讓未在場的人物因後來傳聞而改變態度，應在**真正接收到資訊的後續事件**才結算，且可以只改主觀態度、不改客觀事實。
- **關係數值非必然獎勵**：幫忙成功不代表一定增信任，導師理性處理不代表所有人認同；`5-1` 信任與 `5-4` 不滿可同時高，不能自動互相抵銷。

### B-4　已有聯繫但缺少持有者的例外

**接觸與關係初始化問題需獨立處理**：現有 `contact` 事實交易可建立兩個合法角色的初始關係，但是否適合因某一故事結果立即建立新定向關係，需要先核對玩家與NPC的真實接觸、先後操作順序和同一交易的原子性。

- 若兩人原本已有關係，直接在其既有方向變更。
- 若兩人首次在本次故事相遇，**只有真的發生接觸、且既有流程合法建立關係後**才能調整；必須確認 `contact` 建立與後續變動在同一合法提交序列內，不得以角色出現在同一個事件名單作為實際見面的證據。
- 若尚無合法關係，結果仍可留下客觀事實與人物個人情緒改變；關係變動保持不成立或待處理，**不可默默略過已宣稱成功的關係效果，也不可自動補成已有熟識關係**。

### B-5　與A項持續問題契約的銜接

關係數值變化**不是問題狀態的唯一證據**。例如學生A與B的信任增加，並不表示兩人的衝突已正式和解；需要一筆可追溯的和解／撤回指控等客觀事實，A項的「問題已收束」查詢才可以變更。

反之，問題在高二和平解決後，雙方仍可能互相不滿。高三新事件可同時讀取**A項同一問題的收束證據**與**B項兩條方向性關係**，不互相覆寫。

### B-6　不大規模測試的最小驗收門檻（實作時才執行）

1. 同一事件A與B皆在場，A→B信任變動；B→A及無關C→A保持原值。
2. 同一筆結果同時更新A→B不滿、B→A尊重，確認方向、代碼、數值收據及再次提交不重算。
3. A與B原本沒有關係時，不允許任意偷建；合法首次接觸、關係初始化、再變更的順序正確。
4. 未在場也未得知事件的家長不自動改關係；日後合法知情後才能依新事件結果變動。
5. 三學年存讀、學期合法重試後，歷史結果與既有關係一致，不重演已保存的變更；無關存檔欄位保持不動。
6. 普通日常允許 `relationshipChanges` 不存在／為空；並不強制任何人好感增減。

**B項階段判定：既有關係持有者與數值結算器可用；正式故事作者語法、合法關係建立時序與跨人物綁定仍待小幅工程接線。** 本節不宣稱程式已完成。下一項C應引用A項根事實及B項的實際關係方向，不能再創造一份「友好度」或依關係值猜測是否結案。

## 十、C項設計契約｜跨主題共享具體問題的事件資格與抽選（2026-11-15；規格提案，未實作）

**設計目標：** 不用替每個故事寫死「高一事件A→高二事件B→高三事件C」，而是讓不同主題的正式候選以**同一個具體問題、當事人、實際知情與當前狀態**取得合法資格，再由現有事件抽選決定何時發生。此項沿用A項問題來源／狀態及B項定向關係，**不新增第二個候選池／Storylets引擎**。

### C-1　既有能力與確實缺口

- `src/runtime/event-candidates.js` 的 `validateEventDefinitions`、`buildEventCandidates` 已有 `eligibility.facts`（明確事實ID）、`history`（歷史分類門檻）、`numeric`、`knowledge`、`companions`、`affiliation`、`enrollment`、`dayKinds/slotIds/from/until` 等資格，另有 `repetition` 冷卻／互斥及6數值權重；`eventIndex` 已按本輪世界建立 `facts` 與人物歷史索引。
- 現行 `eligibility.facts` 依**預先指定的確切 `fact.id`**查找，尚無「依當前人物和問題類型，動態選出某件未解具體問題」的正式資格；`Hxx-x` 計數不能保證問題仍有效／已收束，也不能分辨同一學生的兩件同類問題。
- `validateEventDefinitions` 強制 `cumulative` 有非空 `eligibility.history`、`direct` 不能附帶該歷史門檻；C項**不可為方便直接解除此限制**。本規格新增的是問題綁定查詢（候選的另一種資格來源），不是假冒累積歷史次數。
- `src/runtime/story.js` 的條件替換目前僅接受數值範圍及精確事實ID，尚不能保證普通對話已經能直接查「問題仍有效」；故**事件候選合資格**與**事件階段內台詞／選項依據**需分別核對，不能因候選通過就宣稱故事內所有動態文字已自動生效。

### C-2　必要的最小作者語意（名稱暫定，尚非現行合法欄位）

對真正需要前因的子事件，可在既有 `eligibility` 下提出**可選**的 `issue` 條件（或等價編譯期契約）；純日常、首次出現的直接事件不要求此欄。建議作者宣告：

| 欄位／語意 | 最小責任 |
|---|---|
| `kind` | 符合A項已定義的具體問題種類（例：上學安排需協助），不是單一 `Hxx-x` 分類碼 |
| `subjectRole` | 需與候選主要 `participant` 或已合法綁定的具體人物ID一致；不得任意搜尋別人的隱私 |
| `status` | 要求 `active`（仍有效）、`closed`（有收束事實）或明確其他可證狀態；**unknown不符合宣稱已解決或仍有效的硬性資格** |
| `binding` | 執行時回傳**具體 `rootFactId` 與證據事實**，而不是只回 `true`；後續事件的實際根須可追溯 |
| `knowledge` | 若劇情要求老師／家長／學生當場引用具體內容，必須另有合法的原有知情／主張資格，不以 `issue` 的客觀存在自動授權台詞 |
| `quantifier` | **預設存在至少一個合格的具體問題**。若需全部或特定組合，應用可檢查的有限AND規則；不開放任意無界布林式或即時程式碼 |

此處是設計介面，不代表目前可直接將 `eligibility.issue` 放入正式定義：既有驗證採精確欄位白名單，實作時須同步更新資料驗證及候選查詢；不修改A項根事實與B項關係的權威來源。

### C-3　決定性、唯一性與候選綁定

1. **先篩角色與合法世界**：以已有的學籍、日期、接觸、知情及事件資格限制取得合格當事人，再對其查詢A項問題的只讀索引。
2. **先綁具體根，再判斷故事**：若該人物有多件同類有效問題，**不任選一件**。可以各根建立一個獨立合資格候選（其候選身分包含 `definitionId + participantIds + rootFactId`），或明確定義此子事件只能在唯一問題時出現；不得以陣列第一筆偷選。排序必須穩定，不依物件迭代碰運氣。
3. **資格與文字使用同一根**：被選定時保存／鎖定該次候選所綁 `rootFactId` 及必要證據，後續台詞與A項`open/progress/close`均回指它；不能在故事開始時重新搜尋並指到另一件同類問題。
4. **真實知情不越權**：只讀索引的客觀問題可用來判斷世界資格，但NPC只能引用自己確實知道的版本。若只是傳聞、尚未確認，需用 `claims/knowledge` 表達，不能拿 `fact` 當作NPC已證實的真相。
5. **版本及時序**：由本次世界修訂決定候選；正式抽中／接入之前，仍需使用既有的當前資格與時段確認。被接納後沿用本事件的已鎖定狀態與事實，不能因下一輪索引變化把同一已開啟事件換成另一個問題；跨日後續不偽裝成新事件。
6. **不可強迫觸發**：`issue` 只能決定「是否合格、綁定哪個根」，**不代替原有六項加權、K倍率、低曝光修正、合法新事件額度與重複排除**。關鍵校務義務的時限另由既有程序推進，不能用提高事件出場機率充當依法／依校務應完成的程序。
7. **不因共享問題合併事件**：T04出缺勤、T08家庭、T09親師溝通、T02升學等是不同故事身分，可引用同一 `rootFactId`，但抽選、互斥、數值結算及事實結果各自獨立。真正同一未結問題避免重複處理，應利用候選根身分及既有重複／排除機制，而非硬將全部不同主題視為同一事件。

### C-4　跨主題情境：高一到高三的自然分流

**共同起點：** 高一某學生多次遲到，教師確認「上學安排仍有待協調」並建立具體問題根F1；這不代表已查明家庭責任或學生故意違規。

- **T04類出缺勤後續**：只要F1仍有效且有當下合適的出缺勤事實，可以抽中另一次校園協調；教師可以檢視已確認的遲到事實，不能預設家庭因素。
- **T08類家庭生活事件**：若後續有可觀察或可查證的家庭資源／照顧資訊，才可據此推進F1；家庭問題可能尚未被教師知道，敘事不能先揭露。
- **T09類親師聯絡事件**：若家長與教師有合法聯繫及知情條件，可討論交通／接送協助，留下F1的進展或正式收束事實；一位家長未回覆不代表另一名家長必定知情。
- **T02類升學事件**：若高三時F1仍有效，事件可參考真實處境調整時間安排；若F1已收束，普通升學事件仍可發生，但不得再寫「一直沒人協助上學」。
- **自然結束路徑**：高一下或高二已改善即可提前結案，不要求高三回收；若多年未有新事件，只能表示尚無新的確認資料，不能自動判定問題已消失。

### C-5　多條件、冷卻及不可達問題

- 初版只需**有限且可靜態檢查的合取（AND）**：現有正式資格與一個具體問題條件共同成立；若劇情有「甲或乙」兩種不同前提，可由兩筆真正不同的候選定義、有限預寫替代條件或明確的OR語意處理，**不可用動態任意運算碼**。
- 靜態檢查應拒絕不存在的 `kind`、非法角色及在語意上必定互斥的要求（例如同一根同時必須 `active` 且 `closed`）；對只有執行期世界才能確定的組合，標示「需情境證據」，不可假稱靜態工具已證明可達。
- 同時保留現行 `same-day-instance`、`active-topic-participants`、`topic-cooldown`、`same-objective-cause` 和 `explicit-exclusion` 規則；根綁定引入的新候選鍵不可使**同一日、同一問題**被不同ID重複結算，也不能因此阻擋無關問題。
- `cumulative` 的歷史計數要維持原功能；若某個`cumulative`再同時要求A項具體問題仍有效，兩種資格皆應成立。不得因新增`issue`而偷偷讓既有`direct`接受非空`history`。

### C-6　最小實作範圍與相容性

先依A項確認根／收束語意可由世界正式事實讀取，才擴充 `validateEventDefinitions` 的可選條件、`buildEventCandidates` 的當事人問題篩選與**候選根事實綁定**，以及故事接納／讀取的合法來源一致性；若單純在候選處理合格、故事卻無法使用同一根，則**不算接線完成**。

可保留現有候選ID/資源ID契約，將具體問題根作為候選實例身份的一部分；避免同一`definitionId`在不同存檔表示不同故事語意。若需要新欄位，正式實作應同時提出驗證及舊存檔預設行為（沒有新增`issue`資料的舊事件維持原邏輯），不得直接修改已保存的歷史交易或更改 `save v2` 外殼。

### C-7　代表性驗收設計（此輪不執行測試）

1. 一個學生有F1、F2兩件同類未解問題：候選各自綁定正確根，不混用、不能偷偷只取第一件。
2. 高一F1有效、高二T08合理推進、高三T02引用；中途收束F1後，「仍未解」專屬事件不再合格，普通升學事件仍有機會出現。
3. 沒有合法知情的學生或家長不能在台詞中提到F1；即使數值高、關係好，也不能跨越知情邊界。
4. `direct`保持沒有歷史門檻；`cumulative`仍須歷史門檻，兩者可使用合法問題查詢，且不破壞六項權重。
5. 同日多候選／冷卻／互斥／跨日等待／存讀後，具體根身分一致、已結算效果不重複。
6. 普通日常沒有`issue`條件，沿用原本所有抽選規則，無須額外製作伏筆。

**C項判定：既有事件資格與抽選機制可用，但「動態具體問題查詢→候選綁根→後續故事使用同一根」目前沒有正式資料契約／實作。** 預期需要小幅擴充候選資格、身份與故事接入；不需新引擎。下一項D只評估本輪多個候選共用索引、效能與存檔界線。

## 十一、D項設計契約｜三學年因果索引、效能、儲存與相容（2026-11-15；規格提案，未實作）

### D-1　現有成本來源與不得誤判的部分

- `src/runtime/event-candidates.js` 的 `eventIndex(world)` 已以一次呼叫建立 `facts` Map、歷史分類、事件狀態、曝光、主題人物／定義／互斥索引；但**每次重新查詢候選**仍會重建。長期因果新增的問題索引應能與此索引**共同建構或共用**，不在每個候選和每個人物身上重新掃描所有事實。
- `src/runtime/story.js` 目前 `storyState` 用 `history.findLast` 尋找最新事件階段；`src/runtime/model.js` 的 `findFact`／`findEvent` 有驗證期 WeakMap 參照索引與一般查詢退回線性搜尋。這是**重複查詢可最佳化的具體位置**，但不能不經量測就斷言它已造成延遲。
- `src/runtime/transactions.js` 的 `prepareWorldOperation` 會驗證輸入、在分離草稿執行交易、再驗證輸出；`src/runtime/model.js` 明確校驗世界、事實、因果、知情與歷史。三年歷史的總成本還包括**完整世界複製、資料校驗、交易收據及存檔序列化**，不只有抽選候選。
- `src/storage/format.js` 使用邏輯 save v2、`runtime.version=1` 與嚴格欄位驗證，並檢查 opening 與 current world 的歷史前綴一致；`src/storage/indexeddb.js` 的實體存檔支援 Gzip、分頁、雜湊完整性與舊編碼後備。**壓縮只能改善儲存位元組，不會自動減少執行期間世界遍歷與物件複製成本**。
- **目前沒有本輪量測數字**：不填寫憑空估計的三年檔案大小、平均載入時間、最大歷史筆數或虛構的效能改善百分比。

### D-2　推薦架構：一份權威紀錄＋必要的結構化因果操作＋可重建的查詢投影

**不再把「絕不新增欄位／檢查點」當成硬性目標**。優先追求三年正確性、撰稿簡潔、執行成本及舊存檔相容：

1. **權威寫入**：A項 `open/progress/close/invalidate` 的具體問題操作應具備可驗證的結構化語意。推薦先評估隨正式事實交易保存受檢的因果操作（`rootFactId/kind/actors/operation/basis` 等）。這是**新增原本缺少的事實意義**，並非重複的問題資料庫；若現有 `fact.data` 無法清楚承載，允許新增**一個與既有原子提交綁定的正式因果紀錄類型**，但不得設立不受同一交易驗證的第二條可變問題狀態。
2. **只讀投影**：從已驗證世界一次建立 `factsById`、`factsByPerson`、`issueByRoot`／`issuesByPersonKind`、`latestStoryByEvent`、`knowledgeByActor`、`activeEventsByTopicPerson` 等**依需要選用**的索引。不要把所有可能的索引強制同時建完；A、B、C只讀同一修訂的索引視圖。
3. **問題狀態推導**：同一 `rootFactId` 的最新合法結構化操作形成查詢結果；「已結案」須有正式收束證據，「不適用」不能冒充已解決，「無法判定」不能被當成已收束。不同根仍相互獨立。索引不得依文字關鍵字、自動推測同學知道什麼。
4. **生命週期與版本**：第一版可以採**每次新的合法世界修訂就失效**的記憶體查詢索引；使用 WeakMap（以實際不可變的世界物件作鍵）或明確的 `attemptId/revision` 與資料身分檢查。存讀、學期重玩、匯入及世界版本變更必須重新建構；不能讓兩個存檔因 revision 相同而錯用同一份索引。
5. **可選的加速檢查點**：如果量測顯示每次重建投影或驗證完整歷史確實過慢，可以加入**帶來源修訂、摘要雜湊、版本與可重建驗證的檢查點**。其身分是衍生加速資料、可丟棄、可重算，不是另一份與世界事實競爭的權威；不得只憑檢查點跳過原本必要的因果與存檔完整性檢查。
6. **無需預先建立龐大問題圖譜**：只對確實建立問題的事件做A項結構化操作；普通校園日常不加問題記憶，不強迫48項數值及所有人物之間建立全連接索引。

### D-3　執行期資料、歷史歸檔與容量原則

- 完整遊戲世界保留原有可追溯 `facts/history/claims/knowledge/disclosures/effects/commits` 與必要的學業、校務歷史；**不為了節省容量任意刪除已用於重算、重玩、事件資格或筆記本的紀錄**。
- 若三年累積的重複全文文字確實造成容量壓力，**優先評估資料正規化與結構化來源引用**（例如穩定的資源ID、內容版本與必要快照），而不是在舊存檔中剝除能解釋歷史的資訊；已開啟的故事繼續使用其確認時的內容版本，不以新版本悄悄改寫歷史。
- 存檔壓縮、完整性檢查、資料格式、版本遷移與反向讀取必須各自分開評估。新內容可選欄位**不必然要求改 save 外殼版本**，但若真的更動受檢的世界結構或歷史語意，就須提出明確版本及一次性遷移策略，不得假設所有舊存檔可直接讀新格式。
- **舊資料誠實降級**：舊世界中未曾建立結構化問題的普通事實仍合法，預設「沒有可證明的具體問題根」而不是憑文字猜成某件未解承諾；舊事件與數值收據不回填假想來源，不在讀檔時重結算。
- 可選的查詢檢查點若損壞、版本不合或來源摘要不符，應丟棄並從權威世界重建，不應使正常存檔永久無法開啟。

### D-4　新增結構的評估門檻：何時該加、何時不該加

| 需求 | 建議決策 | 理由 |
|---|---|---|
| 要明確記錄「某件承諾已履行」 | **應補結構化因果語意** | 單靠描述、`H`碼、`causeIds`不能可靠推斷 |
| 故事修改A→B關係 | **應補合法 `relationshipChanges` 作者欄位／編譯接線** | 數值引擎已有`relationship`持有者，只缺故事綁定 |
| 不同主題要找「同一未解問題」 | **應補 `issue` 資格與根綁定** | 不能用靜態指定的事實ID或歷史分類次數完全取代 |
| 每輪多次查詢三年歷史 | **先共用記憶體查詢投影** | 一次建索引即可服務A～C；不增永久資料 |
| 長期存讀／驗證確實過慢 | **可增加可重建檢查點或分段驗證** | 有實測證據且不犧牲整體正確性才導入 |
| 另建一套可獨立更新的 `storyThreads` 狀態表 | **原則不建議** | 容易和世界事實、交易收據出現雙重權威 |
| 改動K、六項權重、48欄或新增第二事件引擎 | **本問題無必要** | 這些不是目前跨事件因果缺口 |

### D-5　實作時的少量驗證及量測，不做完整三年模擬

1. **正確性**：同世界多次查詢一致；事件交易後新世界即更新；舊世界不受影響；重新讀檔、匯入、失敗重試不得讀到錯誤根或知情。
2. **雙根與多人物**：同學生兩件承諾只收束正確一件；A→B與B→A不混用；不知情人物仍無合法引用。
3. **交易不重算**：同一份事實與效果重送不造成二次數值增減；檢查點不作為結算來源。
4. **局部量測**：以現有精準測試種子，分別觀察候選索引建構、候選篩選、單次世界操作準備／驗證、存檔序列化、解壓與驗證的**可核對耗時與記憶體**。若需大型資料，可用專用測試資料觀察不同歷史長度趨勢，不依賴反覆跑完整三年玩法。
5. **容量與回退**：記錄原始／壓縮儲存位元組、可選檢查點大小；若檢查點無法通過來源驗證，從原世界重建且遊戲結果一致。
6. **編輯驗收**：有結構化問題操作的故事才用A／C通用因果查詢；普通日常不需多填欄位，不為滿足測試而假造長期伏筆。

### D-6　A～D聯合架構建議與修訂優先序

**本節更新先前過度保守的措辭：原始規格不是不可修改的法律。必要的新增欄位、經驗證的世界紀錄類型與衍生檢查點都可以提出，判斷標準是正確性、內容製作成本、效能、存檔相容與後續維護，而不是「欄位越少越好」。**

推薦採以下實作順序（尚未授權實作）：

1. **先A**：把具體問題的開啟／推進／收束定義為**正式交易的一部分**；選擇擴充`fact.data`或同交易的新因果紀錄時，以驗證簡單、來源可追溯和舊存檔清楚降級為準。先能唯一辨識一件問題，C才有可靠來源。
2. **再B**：擴充正式故事結果中可選的關係效果，直接結算既有定向關係四欄；首次合法接觸與持有者存在性必須受檢。
3. **再C**：在既有候選引擎補可選問題資格，將具體`rootFactId`綁定候選及後續故事，不改`direct/cumulative`原歷史限制、K及事件額度。
4. **最後D**：讓抽選、讀故事及人物歷史共用修訂級只讀索引；依小範圍量測決定是否另做持久衍生檢查點／分段驗證，**不預先承諾需要或不需要**。
5. **到此才恢復18-B內容量產**：回看T10-03現有20則是否適用A／B／C，但**不要求全部寫伏筆、全部改數值，或重做20則**；先用三類真正跨主題代表情境驗證新架構，並與撰稿流程分離完成語意審查。

**D項階段判定：資料契約可完成；效能瓶頸尚無實測結論。工程可在有證據時合理新增必要欄位、投影、檢查點或版本遷移。** 不把「避免大型重構」誤寫成「拒絕必要修改」，也不把可選最佳化誤寫成已實作。
