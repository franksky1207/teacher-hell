| **獨立稿件與審查檔** | 五區塊Markdown、符合05的審查JSON，均放在專案內非測試素材目錄，`lock`記相對路徑與SHA256 | 不能只存一段聊天內容、沒有實體檔就宣稱鎖定 |
| **試作與測試素材** | `test/fixtures/`、S0451測試稿、S1708／S0600／S1461等只供隔離核對 | **一律不計正式量產，不能污染帳本** |

**合法狀態轉移（現有CLI已支援）**：

```text
新摘要 ── propose ──> proposed ── reserve ──> reserved ── lock ──> locked
                            ^                   |
                            └───── release ─────┘
proposed／reserved ── reject ──> rejected（不可再改；使用新draft_ref）
proposed／reserved ── revise ──> 原狀態、但摘要／標籤更新
```

- `proposed`只表示摘要已合法登記，**不占種子**。
- `reserved`代表某組S種子已獨占暫用，不得被其他候選使用，**未通過完整稿審查**。
- `locked`才代表該篇通過當前CLI可驗的機械／基本審查存在性，配正式故事ID並計入正式進度；其內容品質仍需05的GPT實質審查，不可因程式允許`lock`自稱全部自動驗證。
- `rejected`保留被退件資訊與原因、不占種子，不能在原`draft_ref`直接重開。要修稿又重新投稿須新候選識別。
- **已鎖不可直接`release`／`revise`／`reject`**，原稿與審查SHA保存。事後確定重大內容錯誤時，依新增的`revoke`撤銷（原負責者、具體原因、預覽及revision防護），不得改原稿與審查檔。`revoked`保留原ID、原種子ID和兩份SHA證據，卻不計有效篇數、日期配額或題材占比；其種子可重新暫用，ID永久不重配；`audit`仍須檢查原始檔案。撤銷不會自動生成替代故事。

**同日重疊的T配額分配問題**：現行CLI是每篇T指定一個合法主題`t_topic_id`與一個創作歸屬`date`，合計同日已鎖不超過6；**創作時應核算主題與前後窗口各自需要多少篇**，不能因兩個主題共用一天就從兩邊各認領6而多算648。**第10批已定向驗證重疊主題身分獨立、同日六篇及跨日查詢不新增配額；T20原日期完全不變**。

### 第10批稿件與帳本接口

- T稿第1區既有`required_window`鍵與欄名不改，填**唯一池ID**，例如`T1-4:before`；不再接受僅填一個日期、自由文字或其他主題的池。必要的敘事知情／在場條件仍填`required_conditions`並由GPT審查。G稿的T主題與窗口填「無」，不需T池，不能挾帶T池ID。
- `propose --date YYYY-MM-DD`是配額日；`poolId`直接取自稿件`required_window`，不另設可與稿件分歧的CLI選池參數。配額日必須屬該池。`revise`不可變更既有主題／池身分；`lock`再次比較稿件與候選池，`validateLedger`拒絕不合法的主題／池／日期。若需換池，須依既有`reject`流程退件並釋放種子後另建候選，不得偷改。
- 唯一最小帳本新增欄位為`poolId`（T必填、G為null；既有G可省略）；schemaVersion、狀態、revision、配號及鎖定扣額時點不變。舊T紀錄若缺池ID會明確拒絕，不依日期自動猜池；正式帳本目前空白，因此不需要也沒有執行正式遷移。
- 唯讀查詢：`node scripts/manage-story-production.mjs windows --topic T1-4`列來源池；`windows --ref REF --ledger FILE`列候選的`quotaDate`及池內全部日期。主題查詢與候選查詢為二擇一用途。函式與完整資格邊界見[02時間資格](./02-事件分類與時間資格.md#第10批已實作的最小窗口契約)。
- 第09批情緒標記／六選三／七證據保持強制。單池容量不額外乘主題；108個不重複配額日×6仍為648，不把28池日期加總的119×6當正式容量。

## 3. 單一GPT的實際CLI命令

在**專案根目錄**執行，且使用本分支的`scripts/manage-story-production.mjs`。所有可寫入的操作**預設只預覽、不修改帳本**；確定通過再加`--apply --expect-revision N`，N須為當下正式帳本`revision`，不是從上次記憶猜的。每次成功寫入`revision+1`。

### 3.1 先查狀態、種子與重複候選（只讀）

```bash
node scripts/manage-story-production.mjs status
node scripts/manage-story-production.mjs audit
node scripts/manage-story-production.mjs available --seed S0001
node scripts/manage-story-production.mjs duplicates --ref T-DRAFT-001
```

- `status`列出已鎖T/G、未使用／暫用／已鎖種子、各狀態候選、T/G剩餘容量，以及各標籤出現次數（`tagCounts`）、百分比（`tagPercent`）與總分母（`tagOccurrences`）。`audit`核對locked稿件與審查檔SHA及帳本結構；`available`查指定種子是否已被占用。
- `duplicates`以目前帳本中未退件的摘要做相似片段搜尋；**可能回報多筆相似或0筆，不代表GPT已完成真正語意查重**。同批／跨批、T/G核心相近者仍要GPT逐篇對照；實際比較與結果記05的`duplicates`證據。

### 3.2 摘要過關後，先propose（指令示例）

```bash
npm run content:draft-check -- --input work/your-summary.md --stage summary
node scripts/manage-story-production.mjs propose --ref T-DRAFT-001 --owner ChatGPT --file work/your-summary.md --date 2026-07-20
node scripts/manage-story-production.mjs propose --ref T-DRAFT-001 --owner ChatGPT --file work/your-summary.md --date 2026-07-20 --apply --expect-revision 0
```

**示意而非固定值**：`T-DRAFT-001`、`2026-07-20`、`revision 0`僅用來展示語法；實際每篇必須核對T20主題是否包含指定日期、目前帳本版本與合法窗口。T需要`--date`，G不能附`--date`，且T648鎖滿以前不能propose G。

### 3.3 檢查合法四碼後reserve，再撰寫選項與全文

```bash
node scripts/manage-story-production.mjs reserve --ref T-DRAFT-001 --owner ChatGPT --seed S0001 --reason "這組四碼可分別推動師生、親師與導師決策的實質衝突"
node scripts/manage-story-production.mjs reserve --ref T-DRAFT-001 --owner ChatGPT --seed S0001 --reason "這組四碼可分別推動師生、親師與導師決策的實質衝突" --apply --expect-revision 1

npm run content:draft-check -- --input work/your-full-story.md --stage choices
npm run content:draft-check -- --input work/your-full-story.md --stage full --json work/story-check.json
node scripts/manage-story-production.mjs duplicates --ref T-DRAFT-001
```

**種子與故事要互相適配**：`reserve`須有至少12字元的原因，不能只寫「故事可用」；`choices`前必須有四碼與合法持有人、恰一個情緒選項及六普通候選隨機取三的**獨立審查留痕**。第09批已機械驗證四選項恰好一個情緒及其與審查映射一致；行動差異仍須GPT審查。

### 3.4 修稿、釋放種子或退件

```bash
node scripts/manage-story-production.mjs revise --ref T-DRAFT-001 --owner ChatGPT --file work/your-full-story.md --reason "修正起因與教師困境，使其和既有故事有實質差異"
node scripts/manage-story-production.mjs release --ref T-DRAFT-001 --owner ChatGPT --reason "四碼與主角的合法持碼資格不相容，退回可用種子池"
node scripts/manage-story-production.mjs reject --ref T-DRAFT-001 --owner ChatGPT --reason "核心困境與已鎖故事實質重複，終止本候選"
```

- **每個可寫入指令正式執行時**仍須加`--apply --expect-revision <當下revision>`；上列先是只讀預覽。
- `revise`可在`proposed`／`reserved`修改摘要與tags，**不能變更`draft_ref`、T/G類型或T主題**；若已reserved，稿內種子若有填必須和占用S一致。它**不代表已同步更新獨立Markdown全文**，修改原始檔後仍須重跑受影響stage與內容審查。
- `release`只適用reserved，變回proposed並釋放種子，保留候選與摘要；`reject`會結束候選，需附原因。若創作須改T主題，**先reject原候選並建立新的`draft_ref`**，不可用revise偷換。
- 不合格優先局部修，不因一次失敗就重寫所有8個R；真正換皮或不合規格須拒稿而非靠機械過關。

### 3.5 審核核准後lock，並audit確認（示意，這批不操作正式帳本）

```bash
node scripts/manage-story-production.mjs lock --ref T-DRAFT-001 --owner ChatGPT --file work/your-full-story.md --review work/your-editorial-review.json
node scripts/manage-story-production.mjs lock --ref T-DRAFT-001 --owner ChatGPT --file work/your-full-story.md --review work/your-editorial-review.json --apply --expect-revision 2
node scripts/manage-story-production.mjs audit
node scripts/manage-story-production.mjs status
```

**必要先決**：稿件已完整`full`機械通過，與帳本中已登摘要／標籤／種子一致；審查檔有明確`verdict="approved"`、`reviewer="ChatGPT"`、七項各至少16字元的具體核查理由及**05新增的六選三紀錄**；T單日已鎖總數未達6且合法，T不超648，G待T648已鎖。若稿與帳本資料不一致，先用`revise`按合法欄位修訂並再審，**不能直接強行lock**。

`lock` 預覽執行鎖定檢查，回傳的 `change.storyId` 為 `null`。成功套用才回傳正式故事 ID。

**提交與SHA**：真正寫入帳本時，工具從原始稿和審查JSON讀檔計算SHA256，記專案內相對路徑；**同一次受版本管制提交須保留對應的完整稿、審查檔與更新後帳本**。已有locked資料時`audit`會重新讀兩檔核對SHA，不能在鎖定後改原稿`story_id`占位；**正式ID以帳本配號為唯一權威**，待正式轉JSON才輸出，轉換器尚未完成。

## 4. 正式審查JSON（第07批文件契約）

使用**一份獨立的JSON檔**，不要把審查塞到五區塊正文。此格式沿用CLI既有七欄必填證據，增補`ordinaryChoiceSelection`作六候選留痕。以下是**結構範例，不代表已有核准故事**：

```json
{
  "verdict": "approved",
  "reviewer": "ChatGPT",
  "storyAndRoles": "逐項描述真實起因、教師角色、職權與客觀事實及當局在籍、在場、知情之審查",
  "fourCodes": "分別說明種子四碼各自如何驅動事件、合法持有者及所受結算的具體因果",
  "fourChoices": "核對A至D各自的不同教師行動、已完成的客觀事實、情緒恰一及其取捨",
  "eightResults": "比對R1至R8不同發展及各種合法數值與八結果等權平均限制",
  "causal32": "已逐格核對A至D對R1至R8共32組路徑，指出可達及不可能格的實際理由",
  "timeAndLaw": "具體檢查本篇合法演出窗口、活動前後池、當事人知情與教師及學校權限",
  "duplicates": "分別記摘要及全文查重，比對疑似候選之核心困境與教師選擇實質差異",
  "ordinaryChoiceSelection": {
    "ordinaryCandidates": [
      {"id": 1, "action": "合法且互異的普通候選一"},
      {"id": 2, "action": "合法且互異的普通候選二"},
      {"id": 3, "action": "合法且互異的普通候選三"},
      {"id": 4, "action": "合法且互異的普通候選四"},
      {"id": 5, "action": "合法且互異的普通候選五"},
      {"id": 6, "action": "合法且互異的普通候選六"}
    ],
    "selectedIds": [1, 3, 5],
    "finalChoiceMap": {"A": "emotional", "B": 3, "C": 1, "D": 5}

```

**驗證分界（第09批更新）**：`reviewEvidence`保留`approved`、非空核准者、七個文字證據欄各至少16字元及非fixture限制，另強制05的`ordinaryChoiceSelection`結構：候選ID為整數1～6各一次、非空行動字串，三個不同中選ID，A～D映射恰一情緒及三中選ID各一次，並與正文情緒標記一致。不驗證候選語意差異、普通行動文字是否同義或實際隨機過程；由GPT補審。32格逐格詳證可另存附件並在`causal32`指出證據位置，不能只寫「已審查OK」。

## 5. 去重、版本安全與正式稽核

1. **兩道語意查重**：`propose`前摘要一次，完稿欲`lock`前全文再一次，皆須包含同批與跨批的T/G候選、已鎖作品，並以起因／核心抉擇／四行動／八結果的實質差異記錄；相似度是**候選提示，不是品質分數或自動通過證明**。現有工具只擋**三欄摘要完全相同**，不能替代GPT跨作品實質查重。
2. **每次寫入核對revision**：預覽通過後重新讀當前帳本`revision`，附`--apply --expect-revision N`；若不一致／遇到遠端SHA版本衝突，**停止覆寫，重新讀取與預覽再作業**。單一GPT製作並不表示多台裝置／不同回合永遠不會有版本漂移；但不為此設分散式多AI搶占架構。
3. **帳本只能在唯一正式來源上修改**：不同分支、離線工作目錄或聊天紀錄不能各持一份同名「正式帳本」後互相覆蓋；正式提交時除revision外還須核對GitHub原blob SHA。現有CLI的本機`.lock`檔只防**同機並發**，不是GitHub跨裝置原子鎖。
4. **日期配額扣除現況**：現有CLI只在`locked`時計入T單日六篇（`propose/reserve`不占用日容量）。**第10批維持只在鎖定扣額**；已驗同日六篇可接受、第七篇lock拒絕，及重疊主題共額／前後池分離。
5. **稽核內容**：`audit`可查已鎖故事稿與審查JSON檔的SHA256、帳本配號／配額／種子重複等一致性；**不能證明GPT寫的故事實質合理**。有任何SHA不一致先追查哪份檔被修改，禁止靠直接更改帳本digest掩蓋。
6. **總進度**：只統計正式`locked`作品。T648完成後方可正式開始G1752；題材G01～G11以**所有已鎖T＋G的有效標籤出現總次數**作100%分母，非篇數。候選、預留、退件、P、隔離fixture均不計。

### 第11批｜單一整合者的 Git 提交檢查

1. 開始前 fetch 指定正式分支。記錄該分支的 HEAD、`git rev-parse FETCH_HEAD:data/story-production-ledger.json` 的帳本 **Git blob SHA**，以及 `git show FETCH_HEAD:data/story-production-ledger.json` 的 `revision`。確認本機正從這份帳本作業。
2. 單一整合者依序處理候選。先跑 CLI 預覽，再用同一基準的 `--apply --expect-revision N` 寫入，並稽核稿件及審查檔。採用 `--json` 時須指定尚未存在的獨立報告檔。
3. 提交前再次 fetch，核對遠端 HEAD、帳本 blob SHA 和 revision，並檢查差異中原有 locked 紀錄（包括兩個路徑及 digest）與原證據檔完全保留。若稿件或審查檔與帳本 digest 一起被改寫，單獨執行 `audit` 無法辨認。須與可信的遠端基準比較並拒絕該變更。
4. 遇到來源變動、push 非快轉、PR 合併衝突或審核時發現基準改變，停止提交或合併。重新同步、預覽並驗證；必要時重做種子選擇及配號。禁止強制推送或選用舊副本的整份帳本解決衝突。

定向測試用暫存 Git 遠端與兩個工作副本重現兩邊 revision 同為 3、帳本 blob 卻不同的情況，並驗證普通 push 拒絕非快轉更新、合併回報帳本衝突。同一路徑的本機 lockfile 只保護遵循 CLI 的寫入；跨裝置依賴可信基準、串行審核及 Git 版本檢查。

`duplicates` 回傳所有找到的未退件候選。變更指令的預覽最多展示十筆，可用 `duplicates --ref REF` 查全數。GPT 在第一關比較摘要，第二關比較全文的實際起因、核心困境、四個教師行動及八個結果，並將比對證據寫進審查 JSON。

量產期間以 `tagCounts` 與 `tagPercent` 參照 [02 的十一類目標與容許範圍](./02-事件分類與時間資格.md)。同篇每個有效標籤各計一次，零作品時各百分比為 `null`。全庫 T648＋G1752 鎖定後才判定比例是否達標。

### 歷史：已鎖定稿的教師四狀態 V1→V2 同 ID 修訂（現行操作見文末V3）

一般 `revise` 仍只處理未鎖候選；本次特設 `revise-locked`，只接受尚未升級的 locked V1，僅可改八行教師四狀態。這是禁止直接改鎖定原稿的窄範圍例外，**不是覆寫原檔**。不接受 revoked、不重配 ID、不改種子、日期、配額、標籤與計數，也不重跑六選三。

1. 原稿與原審查 JSON 留在原路徑，位元組不變。另建 `.states-v2.md` 與 `.states-v2.json`，後者保留原審查所有欄位，新增 `stateRevision`：原 ID／版本／來源 commit／原兩份 SHA、新稿 SHA、前後矩陣、八 R 各四項理由、分布審查、正式 full V2 完整報告及其他欄位未變核對。
2. 管理器逐位元組比對除八組數值以外的全部稿件、核對原與新 SHA、原證據保留與新版 full；不能以附件聲稱 approved 代替正式驗證。語意合理性仍由審查者負責。
3. 每篇先預覽，再以當前 revision、當前帳本原始位元組 SHA256、原稿及原審查 SHA、同一可信 HEAD 寫入。CLI 即時比對本機 HEAD 與遠端 `content/events-production-v1` HEAD；缺參數或不符即拒絕。仍用帳本 `.lock` 與暫存檔原子置換；遠端比較後至推送之間的競爭由提交前再次 fetch 和普通非強制 push 防護，不宣稱跨 GitHub／本機的原子交易。
4. 成功後同一候選的現行 `manuscriptPath`／`review` 指向新檔，`manuscriptVersions[0]` 保存原路徑／SHA／審查資訊，記 `manuscriptVersion: 2`、`stateRulesVersion: 2`、修訂種類與 revision，帳本 history 新增一次 `revise-locked`。不建立第二帳本，也不改既有 lock history。
5. `audit` 核對每個歷史與最新版本的稿件／審查 SHA、識別，以及修訂差異、證據和現行 V2 full。`lockedFilesChecked` 仍是故事數（含 revoked），另增 `versionsChecked` 表示版本數。閱讀器只取 locked 的現行指標，不掃資料夾，因此歷史檔不會成為額外故事。

```bash
node scripts/manage-story-production.mjs revise-locked --ref T-DRAFT-XXXX --owner ChatGPT \
  --file <新稿路徑> --review <新審查路徑> \
  --expect-manuscript-sha <原稿SHA256> --expect-review-sha <原審查SHA256> \
  --expect-ledger-sha <當前帳本SHA256> --expect-head <最新已同步量產分支HEAD>
# 預覽通過後使用相同參數，另加 --apply --expect-revision <當前revision>
```

本機範例是操作契約，不是授權硬湊數值。無法保留原因果而滿足 V2 的篇章維持原指標，不升版本、不改 SHA，留下 blocked 審查紀錄；不得將混合版本的30篇宣稱全部V2完成。每次寫入後重新計算下一篇的帳本 SHA與revision。正式發布仍依[獨立閱讀器SOP](../story-reader-publish-v1.md)，不合併量產故事至 main。

## V3 同故事數值升版（本批只建機制，不操作正式故事）

沿用 `revise-locked`，不撤銷、不重新編號、不重占種子。允許V1→V3或V2→V3；`manuscriptVersions`依次保存原稿／審查路徑、SHA與規則版本，現版 `manuscriptVersion`遞增，`stateRulesVersion=3`。舊版V1→V2仍供歷史稽核。

V3稿只准改八個四狀態欄位的名稱／數值，及新增第1區版本列（格式見04）；其餘文字、四碼／NPC、選項、R及機率矩陣必須逐位元相同。新檔須使用未占用正式成品路徑，禁止覆寫歷史。新審查保留原七項與六選三，`stateRevision`使用 `kind: teacher-states-v1-to-v3` 或 `teacher-states-v2-to-v3`、`version:3`；其餘沿用既有 before／after、32項因果、SHA與完整機械報告欄位。若原審查已有stateRevision，原物件完整嵌入新proof的 `previousRevision`。

```bash
node scripts/manage-story-production.mjs revise-locked --ref REF --owner OWNER \
  --file NEW.states-v3.md --review NEW.review.states-v3.json \
  --state-rules-version 3 --branch feat/story-production-v3 \
  --expect-manuscript-sha SHA --expect-review-sha SHA \
  --expect-ledger-sha SHA --expect-head HEAD
```

先預覽，正式寫入仍需 `--apply --expect-revision N`；分支本機與遠端HEAD、帳本SHA、原稿SHA與審查SHA均須相符。歷史檢查可用明確版本參數；正式帳本新製作只接受V3，舊版本製作只供隔離帳本的回歸驗收。下一批逐篇進行語意審查後才能使用此命令，不能批次自動重新配數。
