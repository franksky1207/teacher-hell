# 第18-B 補充｜ChatGPT 串流中斷、保存點與工作恢復執行規範

> 狀態：2026-11-16 整合 T03 製作經驗，**T04 起正式使用小主題完整任務＋內部可恢復保存點**。本文件只規範 ChatGPT 工具操作、傳輸負擔、GitHub 分支／保存及中斷恢復；故事內容的唯一正式量產／審查流程仍為 [18B-正式事件量產與品質驗收SOP.md](18B-正式事件量產與品質驗收SOP.md)，內容契約依 17-D、18-A 與正式程式。不追溯重做 T01～T03。

## 一、問題與可確定範圍

T02、T03 製作期間，使用者多次回報 **ChatGPT 回覆串流中斷**，發生在故事製作、主控審查、GitHub 讀寫及分支處理等不同工作；重試成功與否不一定，與工作量有關。既有流程已直接寫入 GitHub，**並沒有在聊天畫面大量輸出故事全文**，因此「不要貼全文」不是新的解法。單次處理負擔、工具輸入／回傳量、長對話與平台連線皆可能影響中斷；**目前沒有遙測資料可證實單一根因，也無法保證串流永不中斷**。

**中斷不等於 GitHub 寫入失敗。** 對話的回覆狀態、工具動作是否提交、故事內容是否通過審查，三者必須分開確認。

## 二、T04 起的完整小主題生產方式

- **任務尺度與數量閉環**：每次 ChatGPT 承接完整 `Txx-yy` 小主題，**首輪製作30則完整、實質不同的故事**，不是30個情境標題，也不能在完成20則初稿時停止。**審查先針對有缺陷的稿件進行局部修改、重驗，不能一看到品質問題就刪除**；只有確實無法合理修復，或與已接受稿實質重複且無法改寫為獨立事件，才記錄理由後隔離／淘汰。**最終核可不得少於20則**。若優先修正及必要淘汰後仍低於20則，保留合格稿、另找不同題材，**把有效製作池補回30則完整故事，再審新增及改動部分**；反覆執行直到至少20則通過。通過20～29則可結案，30則以上可全部保留，數量不設上限；不得把 4～6 則改為品質或生產配額。T04 原則以 T04-01～T04-08 八個小主題依序製作，每個小主題各自保存、審查及結案。
- **單次指令不等於單次工具操作**：使用者只需交付該小主題一次指令；探索、整批撰寫、資料保存、必要自檢、一次主控內容審查、局部修正及精準驗收由 ChatGPT 在可用的工具呼叫中接續，不要求使用者每段再說「繼續」。串流中斷無法保證消失，設計目標是讓已提交成果不重做。
- **分段保存，但不拆正式審查批次**：小主題內依資料量、可獨立驗證性與實際操作負擔設定必要保存點；每個保存點只寫入結構完整、ID 穩定且可定位的作者原稿，不把尚未完成的事件當成合格事件。保存點次數不固定、不是每 5 則強制提交，也不增加全批內容審查次數。
- **資料與分支**：沿用既有 `work/18b-txx-yy-authoring.json` 類型的作者來源、相關索引、審查資料與正式 JS 同步程序；**作者原稿為唯一正式內容來源**，不能另建一套相互競爭的 JSON／JS 權威、不能任意新增狀態欄位。T04 起以**每個大主題一條主要工作分支**為預設，八個小主題在該分支持續提交；大主題結案再做一次整合 PR。替代分支只在確有需要時建立，且須清楚標示與主線的關係。**不因 SOP 更新就直接動任何程式或部署。**
- **工作分工**：ChatGPT 是正常產文、審查與 GitHub 管理主力，Codex／Gemini 僅在使用者選擇或實際能力需要時備用；外部模型簽核不是正式放行必要條件。

## 三、工具與保存點的操作規則

1. **一段操作只承擔可恢復的責任**：依相依性分開探索與產文、保存、局部校正、全小主題內容審查、精準工程測試及最後 PR／發布；避免在單一不可恢復工具鏈內同時做全文生成、全量讀取、多檔大型寫入、整批語意審查、整套測試或部署。**不要求使用者每段再下「繼續」**；已確認前一步成功即自動接續。
2. **精準讀寫／最小回傳**：先定位必要契約、主題與既有已接受稿的精簡索引、事件 ID／狀態、GitHub HEAD／檔案 SHA，再按需讀取完整內容；不得每步都重讀 T01～T03 全文、完整大型 JSON／JS 或整段歷史測試輸出。編輯特定 ID 時只核對受影響範圍；若 API 需要全檔替換，應取最新 SHA、保留其他內容並核對差異，不因節流假裝已做到局部寫入。**審查每件待核可故事時仍須取得完整故事及必要因果證據**，不可只看摘要便放行。
3. **保存點要有可驗證證據**：沿用現有來源檔、進度索引與主要工作分支，不為每則事件造新檔案。每次完成可獨立保存的事件集合就提交，核對分支 HEAD／提交 SHA、檔案、主題 ID、已保存事件 ID 範圍及階段（撰寫／審查／修正／隔離／待辦）；可用既有紀錄更新，**不必另設平行進度權威**。工具「已送出」不等於提交成功，寫入後必須確認版本與實際資料。JS 只依現有同步程序生成，不能把草稿直接升成 `ready`。
4. **檢查已有成果再重試**：工具呼叫或回覆中斷後，先讀目標分支 HEAD、提交／檔案 SHA、必要內容及原工作紀錄，判定最後一步是已提交、未提交還是部分完成。已完成的步驟不重寫；未完成者只補該範圍；若檔案被其他提交更新，先重新取 SHA 及核對差異，避免覆蓋。
5. **先修後刪，審查與測試不因保存點倍增**：遇到品質或結構問題，先定位事件 ID 和缺陷、做局部修正與受影響範圍複驗；確認無法修復或與既有事件高度重複、無法改成真正不同的事件時，才記錄原因後隔離／淘汰。撰寫時即時自檢，**首輪30件完整稿完成後做一次主控全批內容審查**；若淘汰後合格數低於20，僅審查補入或實際改動的事件，不重新審已核可且內容未變的故事；對具體問題 ID 集中局部修正；已核可且內容版本沒變的不重審。工程驗收只在有關契約和完成階段精準執行，必要時最後整合再確認，不反覆重跑已通過且版本未變的測試。不跑三年／30年、多 seed、大範圍無關回歸。GitHub Actions 只檢查可程式化項目，不能冒充語意審稿。
6. **簡潔且可核對的回報**：完成量、正式計件量、通過／隔離／待修數、主要問題 ID、版本 SHA、實際執行的測試與結果、下一個未完成步驟；不得把「回覆很短」視為工具一定沒有負擔。若某工具沒有成功證據，標示「未確認」而非宣稱成功。
7. **對話交接以 GitHub 事實為準**：新對話只需定位主要工作分支及最後提交，讀取現有進度索引、已保存事件 ID 與當前階段，直接從第一個未完成項接續；不可要求使用者重述已完成工作。舊對話、歷史 PR 或摘要只能輔助定位，不可凌駕現行 HEAD。
8. **減少不必要的 PR／分支擴張**：同一大主題以一條主要工作分支與最後一個整合 PR 為預設，不用多條互相依賴的 PR 承擔同一小主題的產文及審查。已接受故事不因產生替代稿便消失；確有替代稿時明記原版本、差異、採納／隔離結論及最終唯一版本。
9. **簡單紀錄中斷種類**：只記發生階段、當時操作、GitHub 寫入是否已確認、實際恢復方式／結果，不建立監控系統，不把中斷或恢復猜成必然原因；若短操作仍頻繁失敗，另查 App、連線或平台因素。

## 四、串流中斷恢復 SOP

1. 先識別中斷前原本要完成的**具體操作**與目標分支、檔案／事件範圍；不要直接重執行整批指令。
2. 查 GitHub 目標分支 HEAD、相關檔案 SHA／提交紀錄，以及必要的 Actions／PR 狀態。
3. 若已提交且資料正確：保留現有成果，直接接續未完成階段。若沒有提交：只重做該最小工作單元。若部分提交或版本衝突：先精準比對，再補正剩餘項目。
4. 對**已審核且內容版本沒變**的事件，不重新全批審查；修改過的故事與真正受影響契約才局部複驗。
5. 將最後確認的提交／未完成項記入該批既有紀錄；無法確認時標示待查，**不能把中斷本身當作提交失敗或提交成功的證據**。

## 五、與既有規範的界線

- **品質標準與最終下限不變，首輪製作量明確化**：T01～T16 共 128 小主題；T04 起每小主題首輪30件完整稿、審查後至少20件正式合格故事（全案正式下限2,560）；若不足20件須補回30件有效故事池再審，20不是一開始停稿的數字；四核心仍為世界可信、因果成立、數值有據、文字有生命。不能靠縮短故事、少寫分支、換皮或放寬驗收來換穩定度。
- **既有權威不變**：17-D 內容契約、18-A 檢查器、18-B 一次主控內容審查與集中局部修正，以及 N1～N8、48 數值、日程、事件額度、世界交易、人物資格和存檔均不變。
- **發布門檻不變**：`authored → structurallyValid → reviewed → resolverReady → catalogueReady → publishedInNewCareers`；提交草稿不等於 `ready` 或玩家可抽到。**未經使用者明確授權，不合併、部署、升 `ready` 或發布。**
- **T01～T03 不重做**：T01/T02 已發布 390、隔離 18，見 [正式發布結案](reviews/18b-t01-t02-published-closeout.md)；T03 已完成 201 則放行、26 則隔離並整合部署，見 [T03 正式整合與發布驗收](18B-T03-正式整合與發布驗收.md)。本文件不修改既有正式故事或重新啟動審查。
- **可觀察而非假裝根治**：T04 起用最小中斷紀錄區分生成、審查、GitHub 讀寫、整合或其他工作；若短操作仍頻繁中斷，再查 App／網路／平台因素，不無限縮小正式生產單位或額外消耗模型額度。

**一句話：降低單次操作及回傳的不可恢復負擔，以 GitHub 的真實提交恢復工作；內容標準、驗收門檻和使用者授權全部照舊。**
