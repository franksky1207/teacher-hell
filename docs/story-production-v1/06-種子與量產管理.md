# 06 種子、配額與唯讀工具

- [2,400 組種子總表](../事件四數值三層平衡種子2400組.md)是種子原四碼的來源。T648 與 G1752 共用，每篇 T/G 只持一組，同一種子只能綁一篇。T648 正式驗收完成後才進入 G1752。P 依[獨立日型規格](./02-事件分類與時間資格.md)。
- [T1-001～030 預選清單](../../data/story-production-selected-seeds-T1-001-030.json)固定 30 個 ID 的種子、主題、池與配額日。其餘故事從可用種子選，作業時先查占用。已預選但未有稿的種子保留給對應 ID。
- 每份 Markdown 的第一區填 `story_id`、`seed_id`、T 主題、故事池、`quota_date`，第三區填原四碼。**目前故事產製的 ID／內容來源以故事分支 Markdown 與預選表為準**，既有稿修訂保留 ID、種子及既定分配，以 Git 追蹤。`data/story-production-ledger.json` 是早期 CLI 的另一帳本，不能把其 `locked` 計數直接當成目前故事目錄的篇數，亦不可任意覆寫。
- [T20 日期表](../T1-T6-特定故事20主題與觸發日期.md)維護 28 池、108 個合法日期。重疊主題共用單日六篇。配額歸屬日與播放窗口各有用途。實際可播放須符合池、校曆、在籍、職權、知情與單局一次性。

## 跨日共用池配額及交付紀錄（管理欄位，不取代 02／03／05）

- `quota_date` **只作配額與種子帳務歸屬**；實際可播放日期唯一取自 [02](./02-事件分類與時間資格.md) 與 [T20](../T1-T6-特定故事20主題與觸發日期.md) 定義的 `required_window`。不因同一日期分配六篇，就讓其中故事限定在當天。
- 批次紀錄需能對到故事 ID、種子、池 ID、配額日、池內日期全集、逐日語意驗收狀態（通過／退件／未驗）、審查證據與版本 SHA；**沒有逐日審查就不列為跨日合格**。證據存各活動 `驗收紀錄/`，不要放故事池目錄。
- 實際製作先循 [03 主流程](./03-故事創作精簡SOP.md)，放行條件依 [05](./05-故事品質與驗收契約.md)。工具現有日期／種子檢查只保證可機械判斷部分，不替代語意審查，也不表示 T/G 正式抽選器已接線。

以下是專案根目錄的**按需工具清單**，不是每批必須全部執行（驗收時依 03 選擇當批相關命令）：

```bash
npm run content:production -- status
npm run content:production -- available S0001
npm run content:production -- windows T1-4
npm run content:production -- windows T1-001
npm run content:production -- duplicates T1-001
npm run content:production -- audit
npm run content:production -- audit T1-001 --evidence work/acceptance.json
```

`status` 的篇數與標籤計數反映**故事目錄**現況，並不表示全數通過 05 的 S1～S6；已驗收篇數須由對應 Git SHA 與驗收紀錄判定。正式比例採 [02 的已驗收故事口徑](./02-事件分類與時間資格.md)，由正式驗收範圍統計。 `audit` 查故事格式、四碼、V3、NPC、矩陣、配額及種子唯一性。 `duplicates` 的摘要相似度只供 GPT 查重排序。正式驗收依 [05](./05-故事品質與驗收契約.md) 核對實質查重與逐格審查；已完稿者不必重跑早期摘要階段。

正式驗收時可把證據交給 `audit <ID> --evidence <JSON>`，核對選項映射、NPC 警示、32 格證據與正文權重。審查用檔案可留在 `work/`，或附於正式驗收紀錄。首批[12 篇既有驗收證據](./首批12篇驗收紀錄.json)保存遷移前審查，包括六選三、逐格因果及人物／數值證據。正式審查記錄所審的 Git 版本；日常編輯和 Pages 發布直接使用 Markdown，同版本同範圍已通過的測試結果不重複執行。
