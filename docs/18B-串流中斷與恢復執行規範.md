# 第18-B 補充｜T03 起 ChatGPT 串流中斷與工作恢復執行規範

> 狀態：2026-11-16 討論後的執行流程補充。**只規範工具操作、傳輸負擔、保存及恢復**；故事內容的唯一正式量產／審查流程仍為 [18B-正式事件量產與品質驗收SOP.md](18B-正式事件量產與品質驗收SOP.md)，內容引擎契約仍以 17-D、18-A 與正式程式為準。從 T03 起適用；不追溯重做 T01/T02。

## 一、問題與可確定範圍

T02 製作期間，使用者回報至少十餘次 **ChatGPT 回覆串流中斷**，發生在故事製作、主控審查、GitHub 讀寫及分支處理等不同工作；重試成功與否不一定，與工作量有關。既有流程已直接寫入 GitHub，**並沒有在聊天畫面大量輸出故事全文**，因此「不要貼全文」不是新的解法。單次處理負擔、工具輸入／回傳量、長對話與平台連線皆可能影響中斷；**目前沒有遙測資料可證實單一根因，也無法保證串流永不中斷**。

**中斷不等於 GitHub 寫入失敗。** 對話的回覆狀態、工具動作是否提交、故事內容是否通過審查，三者必須分開確認。

## 二、操作規則：降低單次負擔，不降低內容品質

1. **按相依性與實際負擔分段**：探索、產文、局部校正、寫入、審查、工程測試與發 PR 依必要先後安排；避免在一段不可恢復的執行鏈內同時反覆做全量讀取、跨檔大修改、整批審查、整套測試及部署。分段是內部執行方式，**不要求使用者每段再下「繼續」**；有可用結果便繼續下一步。
2. **精準讀取／最小回傳**：先查檔案路徑、現有契約、所需行數／欄位、指定事件 ID、差異及 GitHub SHA；盡量不重複將整批大型 JSON、JS 或歷史測試輸出帶回模型。必要時仍須完整檢查真正受影響的內容，**不得為減少輸入而跳過品質審查**。
3. **完成一個可獨立保存的單元就提交**：採現有來源檔與工作分支，不為了分段任意新建檔案、複製資料權威或拆爛原有模組。保留提交 SHA、已寫入檔案、對應小主題與事件 ID／範圍；作者原稿、生成 JS、內容版號及審查紀錄仍須一致。保存頻率可增加，**全批內容審查頻率不增加**。
4. **檢查已有成果再重試**：工具呼叫或回覆中斷後，先讀目標分支 HEAD、提交／檔案 SHA、必要內容及原工作紀錄，判定最後一步是已提交、未提交還是部分完成。已完成的步驟不重寫；未完成者只補該範圍；若檔案被其他提交更新，先重新取 SHA 及核對差異，避免覆蓋。
5. **測試不因分段而倍增**：寫作階段只做 18-B 規定的即時合法性自檢，完成一批按受影響範圍進行主控審查與精準工程驗收；有錯僅修實際缺陷及相依引用，局部複驗。不跑三年／30年、多 seed、大範圍無關回歸，也不為中斷反覆重跑已通過且版本未變的測試。GitHub Actions 只承擔可程式化的結構、同步和工程測試，**不冒充 AI 語意與創作品質審查**。
6. **簡潔且可核對的回報**：完成量、正式計件量、通過／隔離／待修數、主要問題 ID、版本 SHA、實際執行的測試與結果、下一個未完成步驟；不得把「回覆很短」視為工具一定沒有負擔。若某工具沒有成功證據，標示「未確認」而非宣稱成功。
7. **對話交接以 GitHub 事實為準**：新對話只需定位工作分支及最後實際提交，按工作日誌／既有追蹤資訊補足未完成項。可另建立簡短進度紀錄，但不能把對話摘要、舊 PR 內文或歷史快照當成比現行 HEAD 更高的權威。
8. **外部工作分工遵守既有節制**：ChatGPT 優先處理可直接完成的工作；大量、可程式化驗證可用既有腳本與 CI。只有實際必要時才使用 Codex／其他模型，不讓工具為了「自主驗收」無限擴張；外部審稿仍由使用者選擇。

## 三、串流中斷恢復 SOP

1. 先識別中斷前原本要完成的**具體操作**與目標分支、檔案／事件範圍；不要直接重執行整批指令。
2. 查 GitHub 目標分支 HEAD、相關檔案 SHA／提交紀錄，以及必要的 Actions／PR 狀態。
3. 若已提交且資料正確：保留現有成果，直接接續未完成階段。若沒有提交：只重做該最小工作單元。若部分提交或版本衝突：先精準比對，再補正剩餘項目。
4. 對**已審核且內容版本沒變**的事件，不重新全批審查；修改過的故事與真正受影響契約才局部複驗。
5. 將最後確認的提交／未完成項記入該批既有紀錄；無法確認時標示待查，**不能把中斷本身當作提交失敗或提交成功的證據**。

## 四、與既有規範的界線

- **品質與計數不變**：T01～T16 共 128 小主題，每小主題至少 20 件實質不同故事（正式下限 2,560），20 不是上限；四核心仍為世界可信、因果成立、數值有據、文字有生命。不能靠縮短故事、少寫分支、換皮或放寬驗收來換穩定度。
- **既有權威不變**：17-D 內容契約、18-A 檢查器、18-B 一次主控內容審查與集中局部修正，以及 N1～N8、48 數值、日程、事件額度、世界交易、人物資格和存檔均不變。
- **發布門檻不變**：`authored → structurallyValid → reviewed → resolverReady → catalogueReady → publishedInNewCareers`；提交草稿不等於 `ready` 或玩家可抽到。**未經使用者明確授權，不合併、部署、升 `ready` 或發布。**
- **T01/T02 不重做**：已發布 390、隔離 18 的狀態以 [正式發布結案](reviews/18b-t01-t02-published-closeout.md) 為準；本文件不修改既有正式故事、不重新啟動其審查。
- **可觀察而非假裝根治**：從 T03 記錄遇到中斷的工作類型、該步是否已提交、恢復是否成功；若小工作也頻繁中斷，再另查 App／網路／平台因素，不無限縮小工作或額外消耗模型額度。

**一句話：降低單次操作及回傳的不可恢復負擔，以 GitHub 的真實提交恢復工作；內容標準、驗收門檻和使用者授權全部照舊。**
