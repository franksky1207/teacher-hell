# 第18-B4｜正式事件量產規格與放行契約

> **定位：規格定稿，非開始量產。** 本文件補充既有 [18-B 正式事件量產與品質驗收 SOP](18B-正式事件量產與品質驗收SOP.md)、[17-D 事件內容量產 SOP](17D-事件內容量產SOP.md) 與 [18-A 工具規範](18A-事件量產工具使用規範.md)。正式作者資料的合法欄位、版本與資格以目前 `main` 的驗證器為準；本文件的**編輯工作表欄位不是遊戲 JSON schema**，不能直接塞進 `validateStory`。

## 一、完成依據、證據與不應誇大的部分

- 基本目標維持 **128 主題 × 每主題至少 20 則實質不同小事件（最低2,560則）**；20是**主題下限**，不是每批上限，也不是選項或變體的計數。不同姓名、換圖、換日、同一事件的 variant、不同對話頁都**不另計事件**。
- PR #59 與 #61～#65 已合併 `main`：歷史截面、具體問題、因果後果與知情、跨主題問題根選取、存讀最低整合。若要用這些功能，依當前合法 `compilerContract:2`、`causality:1`、`issueBindings:1` 等契約編寫，不回到舊版規格推測，也不新增平行問題狀態表。
- Draft PR #60：T10-03原20則隔離試產稿，最新版第十輪報告已有13/13專項成功證據；**不是20則已通過獨立語意審核**，全部仍 `engineering-test`。
- Draft PR #66：03素食餐、13生日卡片、20午餐交接的**三筆另製的隔離因果示範**，不是PR #60原稿轉正。專用[Actions #43677089436](https://github.com/franksky1207/teacher-hell/actions/runs/43677089436) 在提交 `3b908c6` 實際執行 `node --test test/18b2-causal-pilots.test.js`：**3通過／0失敗／0跳過**。此結果證明指定工程案例可跑，不證明所有候選、每種加權變體、三年流程或獨立審稿都通過。
- **本批18-B4只定規格與工作切分**，不建立任何新的正式事件、測試事件、測試腳本或系統；不合併PR #60／#66、不部署、不改事件額度、N1～N8、K、抽選權重、存讀、校曆與程式引擎。

## 二、撰稿前的編輯工作表（非runtime欄位）

每個擬製故事建立一筆可追溯工作記錄，至少記下：

| 區塊 | 必填內容與判斷 |
| --- | --- |
| 身分 | 主題ID、暫定唯一事件ID、版本、作者、資料來源、是否已有正式採納版本 |
| 起因 | 具體可觀察起因、教師職責、事實與未證實說法的區分、必要校務程序 |
| 場景 | 對象範圍、日型與合法時段、現有場景ID、學年限制、非在場者不能自動見證 |
| 因果選型 | 見第三節L1～L5，可多選；說明為何需要或不需要持續問題 |
| 選項 | 四格真正不同的教師策略、自然情緒表現及替換資格；不得「同一策略換語氣」 |
| 結果 | 每個選項及必要variants的可成立客觀事實、未決條件、數值／關係的直接證據、是否跨日 |
| 人物知情 | 客觀當事人、受影響者、實際見證者、傳播者與接受者，哪些仍不知情 |
| 歷史引用 | 如果引用歷史，標註確認來源、問題ID或合法historyCodes、跨主題引用理由、合法結束或失效條件 |
| 去重 | 和本批及所有**已接受**事件比對起因、教師責任、策略、結果與因果；相似即標疑似重複 |
| 審查 | 結構檢查證據、獨立語意審查者及版本、退修理由、再審結論、未驗範圍、正式註冊狀態 |

工作表不能以「有4選項／有兩個variants／有日期」取代事件差異。沒有確實來源的歷史、人際關係與權限，不得藉工作表填字硬編成已知事實。

## 三、因果層級與適用界線

這五級是**編輯分類標籤，可交叉使用，不是需要新增到runtime的等級參數，也不是逐級必修**。

| 級別 | 敘事功能 | 使用條件與禁止項 |
| --- | --- | --- |
| L1 日常當次收束 | 校園趣事、短暫關懷、普通事務，允許平靜或正向結果 | 不強制開問題、不強制數值增減、不為多頁而多頁 |
| L2 人物／關係差異 | 既有數值、合法互動及人物方向性關係影響選項與結果 | 資料碼須有正式定義；**不同人物不是換姓名**；關係只更新有證據的單向邊 |
| L3 同事件跨日 | 因第一天可追溯策略或結果進入不同後續階段 | 後續台詞僅使用各路真實已確認內容；若未有持久證據，寫共同事實，不虛構「已完成」 |
| L4 具體問題／跨主題延續 | 從確認事實`open`具體問題，再合法`progress/close/invalidate`或跨主題選用綁根 | 問題根必須唯一，**前次查詢不等於履行成功**；不憑同學生／同H碼就自稱同一問題；不是所有日常都要長期化 |
| L5 資訊傳達／多人物因果 | 知情來源、說法、機密與真正接觸者帶出後續關係 | 未在場者不自動知情；傳聞不能當客觀事實；**資料權限不足不得憑敘事宣稱文件合法存取** |

任一事件可只用L1，或組合L2+L5，或L3+L4；**不設各級固定比例**。原20則可保留不重做。T10-03代表參考：03（L3+L4）、13（L2）、20（L5，可配L2）；PR #66是技術示範，仍須審稿後才能正式採用。

## 四、核心因果與作者資料契約（以正式引擎為準）

1. **同選項可能有不同合理結果**：`variants`可配置正權重和合法`modifiers`，但不可把「按下查詢」必定寫成「查詢成功」；可以單一結果的簡單選項不強塞機率。人物與教師數值影響應有情境意義，權重不要跨20則複製同一套模板。選項仍遵守17-D的四格、1～2個自然情緒選項及合法`replacement.requires`；高同理心不是「對方已同意」。
2. **事實、主張、狀態三者分離**：`outcome.fact`記真正被確認的結果；`claims`保留主張的來源；`historyCodes`只作分類，不是問題開關。需具體追蹤的事項才透過受驗證的`issueOperations`記`open/progress/close/invalidate`，並由正式投影重建；不得新增可自行修改的`issues.status`。
3. **繼承問題與續篇**：跨主題要先檢核`eligibility.issue`、`bindingContract`與實際`issueBindings`；首次接納與同故事延續不可混成同一資格。開場鎖定的問題根、人物與知情來源不得隨意更換，外部終止、轉學等仍受合法限制。
4. **人物與傳達**：採`compilerContract:2`時依正式支援的`outcome.world`、`relationshipChanges`、`transmissions`和必要`documents`契約；先查真正實際見證、雙人接觸與資訊傳達，再作定向關係效果。未到場的收卡者、未取得授權的人、只是被提及的家長不因事件發生便自動知情。
5. **歷史門檻**：正式契約中只有相容的`cumulative`候選能使用非空`eligibility.history`。原20筆`direct`不能為了湊「有歷史」直接加上累積門檻。需要精準相同問題時應以合法綁根資格，而非單一H碼猜測。
6. **時段、程序及安全底線**：來源不證明的學校作息不能冒稱全校規定；清掃`early`仍是隔離試產假設，正式上架前須核對既有校曆。積水靠電源、清潔劑不適、餐食衛生、個資公開等必要安全動作，應在四選項前先成立；玩家選擇的是不同後續策略，不是是否保障基本安全。
7. **版本與長期儲存**：已確認內容應可重播，修改文字、選項或結果不得悄悄覆蓋已被存檔引用的不可變版本。新稿要先確認正式`validateStory`、`validateEventDefinitions`、內容解析、合法抽選、存讀／attempt的既有契約；不可為一篇故事重寫儲存架構。

## 五、正式量產工作順序與批次切分

**沿用18-B現行七步SOP，不另造八段平行流程：**

1. **題材研究與骨架**：在一主題內先整理候選起因與教師職責，去重後再寫完整故事。若原主題已有試產稿，優先決定可沿用與待修者，不能為了數量重寫已合格的起因。
2. **因果及人物設計**：逐則挑L級，明確規劃誰知道／誰不知道、四種策略、各個結果、證據和適當數值。需要跨主題時，另列引用既有事實及問題根，不額外發明同義問題。
3. **撰寫與局部結構檢查**：使用正式資源ID、版本及17-D作者schema；先放隔離或未註冊資源，不直接標ready。對本批新稿執行`validateStory`、`validateEventDefinitions`與18-A局部檢查，不跑全專案。
4. **與撰稿分開的AI語意審稿**：逐篇核對「已知事實→台詞→四選項→各個可能結果→續篇／跨篇」；退修須提供**事件ID、具體矛盾、修改點、重新查證**。同一模型反覆自檢只能標「自檢」，不得標成獨立審稿通過。
5. **受影響案例精準驗證**：不同結果須有合法來源，讀檔後問題根／人物／知情／RNG不應亂變；僅對本批實際使用的能力挑少量代表案例，每次**最多三組必要情境**。新增錯誤只修對應事件與測試，不重跑無關已通過組別。**禁止三年／30年模擬、全部N1～N8、全專案測試、手機矩陣與PR #60全部20則回歸**；這些工作與必要的正式平衡驗收分離。
6. **跨篇去重與批次體驗檢查**：以累積**已接受**的事件為baseline；同批也互比。對照起因、導師策略、情緒選項位置、結果、日型、場景、人物與因果，防止「換主題仍同一套選項」。允許正向、短篇、荒謬和負面自然混合，不定量比例。
7. **保存版本、證據與決定**：輸出事件清單、審稿表、局部測試命令／結果與未驗項、去重處理表、可能的正式註冊清單；**使用者不必逐篇驗收**。完成製作不等於可上架；需有明確放行與部署決定。

**分批規則**：以「主題＋可維持完整因果與審稿品質的工作量」切分，不訂死每批20則。可以先做較小可審批、逐批補足主題至少20個互異起因；每批應有可辨識的起訖事件ID及baseline快照。**不要因只完成第1批就自動宣稱該主題20／20或全量產SOP通過**。遇實際內容複雜度增加，可縮小施工批次而非省略審稿。

## 六、審稿門檻、記錄狀態及放行

**記錄的四種性質必須分開**：

- `authored`：已完成草稿，不代表內容合格。
- `structurallyValid`：有相應提交的實際結構測試通過，不代表劇情合理。
- `reviewed`：有與撰稿分離的實際語意審稿紀錄、逐篇退修與複審結果，不等於「這個AI自己看過很多次」。
- `resolverReady`、`catalogueReady`：正式內容解析與候選註冊各自實測；`publishedInNewCareers`仍須另外有新生涯合法接入證據。

任何一則以下情況均**不可視為可正式放行**：起因/選項實質重複；玩家選擇被錯寫成保證結果；未取得證據就結案；謠言當事實；人物知情越權；沒有前因的關係數值；時段或法律／校務流程不合法；安全底線只有特定選項才有；修改已發布版本卻未依版本流程。

**品質退件不需要重寫整批**：逐事件退回、局部修正與再審。可接受短日常故事，不因缺少跨日、關係或數值更新而退件。若事件有敏感校務程序（校安、霸凌、性平、身心危機等），需額外查核其程序與資訊來源，不用同一套午餐短劇規範簡化。

**計件規則**：正式可計件的單位是已通過放行條件的**獨立事件ID**，不能用每個結局、每個學生或每個變體灌數；原20件`engineering-test`與PR #66的3件工程示範，現況都計**0正式事件**。正式採用時要依正式版本與ID重新審查並取得授權；不得將「測試通過」自動推成`ready`。
