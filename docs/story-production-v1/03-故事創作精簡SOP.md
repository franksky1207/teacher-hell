# 《教師荒謬地獄》故事量產V3｜03 GPT故事池規劃與單篇創作 SOP

> **數值先行量產版（保留 V3 硬規則）**。本檔是所有 T／G 故事的共用創作 SOP：先規劃 T 故事池，再逐篇創作，之後依核定順序製作 G。稿件唯一格式見[04 五區塊範本](./04-五區塊故事稿範本.md)；人物持碼與時間資格分別依[01](./01-人物數值與四碼資格.md)、[02](./02-事件分類與時間資格.md)；正式品質與因果驗收依[05](./05-故事品質與驗收契約.md)，種子與配額唯讀工具見[06](./06-種子與量產管理.md)。**教師四狀態先排數值再寫八結果；4×8 結局權重先寫故事再依因果判定**。工具負責機械檢查，GPT 負責實質內容審查。[返回總覽](./00-總覽與規格狀態.md)。

## 一、作者開始前只要知道的共同原則

1. **單一GPT負責**構思、查重、改寫、審查證據和文件交接；不需要第二AI，不新增多AI搶種子機制。新增、修訂或全面重寫均採 04 正式格式。建檔即固定正式 ID，檔名與 `story_id` 一致。修訂直接改原 Markdown，沿用原 ID、種子與既定分配。
2. **T先於G**：正式T故事共648篇、20個核定主題與108個不重複合法日期；T648正式驗收後才進入G1752。P/H4不使用T/G的2400種子與此四選一範本。每篇故事只可對應一個合法種子；同局同故事ID只觸發一次。
3. **T故事的活動前後窗口共用池**：活動前5個合法日創**30篇供這5天共同抽**，後2個合法日另創**12篇供兩天共同抽**；前後不互通。**單一日期的六篇是創作配額，不是每日播放六篇或每篇只能在歸屬日播放**；同一天不同主題重疊仍共用6篇總配額。日期表只讀[唯一T20表](../T1-T6-特定故事20主題與觸發日期.md)。
4. **K已取消，絕不可沿用**負1.6／中1／正0.7、舊正中負事件K分類或自行發明替代選篇倍率。四碼的**偏正／偏負NPC選角方向**另屬01人物規格；四選項對八結果的**4／2／1／0**仍屬05品質契約，不能三者混用。
5. **故事獨立、人物依因果選用**：每篇是獨立的真實教師困境，不寫固定續集，不為臨時文字人物另建姓名、ID、數值或下集。學生、校內教職員、當班家長依01常駐資格建槽位；其他班及校外人物只作文字情境角色。
6. **導師身分與任課職權（全部 T／G 共用）**：玩家始終是導師；**任教科目由不同玩家在開局時選定，同一局三年維持一致**，故事不能預設全體玩家教某一科。導師可依職權處理班務、親師溝通及學生輔導；其他任課教師的教法、進度、評量、成績判定與課堂安排由該教師決定。玩家若恰為相關科目任課者，須有合理情境才能以任課教師身分行動；否則只能依實際知情及導師職權關心、協調，不得任意接管別人的課堂。
7. **任教科目自然融入**：每篇創作時主動評估行政工作、同事對話、親師互動、學生提問與校園日常是否自然需要提及玩家任教科目；適合時使用 `{{teacher.subject}}`，不適合就不使用。**不能因追求通用劇情而刻意全部避開，也不能為了使用變數硬塞學科情節或設定使用比例**。同一篇故事以通用因果為主，代入科目不得改變四選項、八結果或數值。`{{teacher.subject}}` 已由共用文字替換器 `src/runtime/story-text.js` 接入正式故事顯示、聊天紀錄與筆記本，並可在獨立故事閱讀器切換九科預覽；故事稿的占位符檢查也已接線。**這是文字顯示代入，不代表 2,400 篇故事已全部接入正式遊戲，也不代表 `{{teacher.name}}` 或 NPC 姓名占位符已完成代入。**無須為每篇新增科目欄位或九份學科版本。
8. **五區塊原稿與獨立審查**：原稿只填基本資料、摘要、四碼與人物、開場／四選項及八結果／矩陣；六個普通候選與中選三編號、查重比較、七項審查證據和工具報告另存，不能塞入04五區塊。
9. **正式進度**：五區塊稿件、`summary → choices → full` 機械檢查與具體內容審查都完成，才計正式篇數。測試 fixture、口頭試作皆為 0 篇。跨池共同規則以本 SOP 為準，28 份 T 時段引導及規劃檔不重複維護。

**共用科目文字**：T／G 劇情以跨科通用為原則。玩家可見文字自然提及任教科目時，使用 `{{teacher.subject}}`。顯示層讀取當局開局所選科目，原稿、事件資格、行動、結果權重及結算皆沿用原資料。

## 二、T 故事池的兩階段創作

### 第一階段　整池主題與摘要規劃

1. 依 [T20 正式表](../T1-T6-特定故事20主題與觸發日期.md)及[唯讀工具](./06-種子與量產管理.md)查詢合法日期、池別及剩餘創作額度。用 `npm run content:production -- windows T1-1` 查主題的故事池，用 `npm run content:production -- status` 查目錄現況與日期占用。重疊窗口按同日各池合計計算，每日共用六篇。配額日與實際播放日分別核對。
2. 讀該池 README 與時段創作引導，掌握當時的班級生活、合法知情、在場、權責及與相鄰池的差異。換池或續作時先查現有正式稿、既有規劃檔、正式種子分配紀錄與最新配額。已成稿可以直接作跨篇比較，沿用原分配，無須重建其摘要。
3. 核對[固定種子總表](../事件四數值三層平衡種子2400組.md)、正式種子分配紀錄及已使用情況。既有分配直接沿用，例如[首批種子預選表](../../data/story-production-selected-seeds-T1-001-030.json)。需要新分配時，用 `npm run content:production -- available` 輔助查詢，再確認正式故事 ID、種子及合法配額，先更新正式分配紀錄，接著將對應資訊填入該池既有規劃檔。依原四碼與合法持有人能自然支撐的情境規劃主題。無法合理落在既定分配的構想，先調整構想。
4. 每篇先寫四欄摘要，即「事件起因、核心衝突、導師困境、故事獨特性」，在企劃中另加一句**T 專屬理由**。指出核定時段實際改變了什麼，例如可知資訊、可行行動、責任或客觀後果。試著換到其他學期或同一活動的另一階段，若核心困境、選擇和後果仍基本不變，就重想時間因果，或考慮是否可獨立成為 G。
5. 合看整池摘要與既有 T／G 故事。逐篇檢查是否像臺灣高中日常、題材與教師抉擇是否有實質差異、時段是否必要、原四碼和人物資格是否合理，以及是否和同池、鄰池或 G 的故事重複。**摘要與四碼因果須寫出本篇特有的事件事實、人物行為與教師實際取捨**：不得大量套用「兼顧雙方」「確認權責」「不能忽略限制」等通用句型，再替換事件名稱充當不同規劃；四碼不能只重述數值定義，須逐碼交代它在本篇如何具體影響行動、資訊、決策或後果。若一句話幾乎可原封不動搬到別篇，僅針對缺乏因果的欄位補強，不因文句相似就重選已分配種子、整池重做或啟動反覆重寫。瑣碎、好笑或溫暖的情境也能形成有代價的真實選擇。引導舉例可自由延伸，題材、角色及情緒皆無新增配額。整池方向合理後再展開完整故事。

每個 T 故事池固定使用與 `時段創作引導.md` 同目錄的 `故事主題與摘要規劃.md`。收到規劃某池若干篇的任務時，讀取該池引導、查詢正式分配後，直接編輯或續修這一份檔案。規劃檔保存構想、四欄摘要與 T 專屬理由，沿用同一檔案維護。

種子原四碼、分配與使用狀態以固定種子總表及正式分配紀錄為唯一依據；企劃僅引用已確認的分配。資訊不一致時，依正式來源修正企劃。每篇正式故事從建檔就使用一個固定 ID，所有正文與後續修改均在同一份五區塊 Markdown。

### 第二階段　逐篇創作

依整池摘要使用 [04 正式範本](./04-五區塊故事稿範本.md)，沿用原四碼、人物資格、四選項、八共用結果與 V3 數值規則，按下節逐篇完成。發現摘要的時間因果、合法行動或數值用途不成立時，回頭修訂企劃及同一份正式 Markdown，再比對連帶受影響的構想與既有 T／G 故事。正式驗收依 [05 品質契約](./05-故事品質與驗收契約.md)另行完成。

## 三、單篇十步可操作閉環：每一步都有輸入、產出和不合格回路

| 步驟 | 輸入與實際動作 | 當步必須產出的內容 | 失敗怎麼處理 |
|---|---|---|---|
| **1 類型與資格** | 確認T/G、20個T主題與合法「前／後」池、實際知情與人物職權；T原始資料讀02及T20表。必要G01～G11實質標籤可先暫貼 | 04第1區：`event_type`、T主題／窗口、必要條件與初步標籤 | 核心節點不具T資格→改合理G摘要或退稿；P或固定制度不可冒充T；活動日全日不抽T/G |
| **2 四欄摘要** | T 稿沿用整池企劃核對過的摘要。先確認**有獨立因果的教師困境**，再填事件起因、核心衝突、導師困境、故事獨特性四欄；明確說明相互合理的要求、權責與實際取捨。不預設兩名學生意見相反、行政刁難、學生反抗或教師犯錯；人物與衝突由事件需求產生，**更換人物／道具／對話不等於新故事** | 04第2區四欄摘要，至少能指出相較既有故事的具體差異 | 缺獨立教師抉擇、只有制度播報、人物對立是為了套模板或與既有故事只換皮→回摘要重構，不浪費種子 |
| **3 摘要初審** | GPT 以當前稿件複查同批及既有故事的起因、衝突、困境、獨特性 | 同一正式 ID 的摘要與實質比較 | 格式問題修第1～2區；換皮重構核心抉擇 |
| **4 核對種子** | T 稿核對企劃的對應種子。首批 T1-001～030 依原預選清單，其他稿查固定2,400組表與 `available`。確認四個原碼皆推動情節，有合法角色能完整持四碼 | 第一區填 `seed_id`，第三區填原四碼與選角方向，並執行 `--stage summary` | 首批固定種子不擅換。其他稿可另選未占種子；無合理四碼因果時回摘要或退稿 |
| **5 角色與事實** | **先從開場、四行動及八結果的預期利害關係盤點重要人物**，再依各自真實行動、職權、知情、在班／監護及可能的長期數值影響建立必要常駐槽位；逐人查本人是否完整持有種子四碼。學生、家長、任課教師與校內常駐人物依劇情和資格判斷，**不預設兩位學生或固定數值人物數量**；有實質作用且合格的成人不得因寫作習慣一律降為背景。僅情境背景人物保留無數值身分；NPC 動態姓名依合法槽位，玩家任教科目依第7點從本局教師設定代入 | 04第3區：數值槽位表、無數值情境角色、四碼各自合法持有人及因果用途 | 持碼／在場／職權／知情不合法，或為湊固定人數添加人物、把實質受影響者當背景→修人物及槽位；影響核心則回第2～4步；不得借用他人數值 |
| **6 四個最終教師行動** | 先產生**1個由本篇人物與情境自然驅動的情緒行動＋6個合法、策略實質不同的普通候選**。四種行動都要有可信的當下動機、教師能完成的客觀事實、可能利益及代價；**情緒不等於愚蠢、暴怒、違規或必敗**，也不須強制有吸引力，避免刻意造一個明顯錯誤項與單一明顯正解。六普通候選去重後**實際隨機取3個**，核對與情緒項的差異和合法性，再**實際隨機排列A～D**；正文 `emotional`、矩陣列與正式驗收紀錄的選項映射須一致 | 04第4區：開場與A～D**恰好四項、恰好1個`emotional=true`**，每項有短句、已完成的教師客觀行動、取捨；**獨立審查紀錄**留六候選簡短內容和中選三編號 | 候選不足／行動只換語氣／情緒選項只為湊明顯錯項→局部重構；候選重複或不可行則先整理候選再重抽，不犧牲品質維持抽中結果；排列錯誤須同步核對選項、矩陣及審查紀錄 |
| **7 數值先行→反向創作八個共用結果** | **先抽組、先排32格、後寫八R**：在既有事件核心、人物與A～D四行動確定後，從05的A～E五組**實際隨機選取4組且不重複**，按精神／熱忱／情緒／掌控各指定一組，再將各組八個數值隨機排列至R1～R8。可使用`node scripts/story-state-matrix.mjs`一次產生候選；機械確認每欄恰為抽中組別、各欄總和−4、平均−0.5、每R最多兩個0。**選定合法32格後固定教師四狀態數值**，再反向寫八個共用結果，讓四項數值的正負及幅度都能從同一段真實因果找到線索：精神反映心力耗損或恢復；熱忱反映投入教育的意願而非單純勞累；情緒反映感受；掌控反映對局面及後續處理的掌握。每R須有不同客觀發展，既有A～D行動事實不能被R抹去。NPC四碼照事件反應另外結算，不受教師A～E抽組拘束 | 04第5區八共用R：各自結果文字、客觀後果、NPC原四碼合法增減與教師四整數；審查紀錄保留四組抽取及32格因果線索 | **只做一次針對性因果檢查**：若某個R明顯沒有支持特定加扣分的線索，只局部修該R的結果文字／客觀後果，原教師四狀態32格不換組、不重排、不重抽。**凡改動任何共用R，皆按第8步重新判定完整4×8因果權重；未受影響者可保留原權重。**修改後核對該R與四個選項的既成事實；若仍有不可解釋的明顯硬矛盾，標記未通過供單篇處理，**不啟動整批反覆重排或無限重寫**；不是因為文字還能更漂亮就要求重做 |
| **8 故事優先→32格因果判定與權重** | **先完成故事，再判權重**：確認開場、A～D已完成行動及八R的客觀後果，先建立32格的「相容／敘事待補／互斥、促進／中性／抑制、具體因果機制」判定，**暫不填數字**；處理真正的敘事缺口後，依05的定義配**4（有具體促進）／2（自然可達、影響不明顯）／1（受抑制或需較不尋常的合理發展）／0（客觀互斥且無合理路徑）**。完成**四列橫向＋八欄縱向**交叉驗證；每列0≤2、每欄0≤1、每列至少一正權重，無0合法。權重不是結局好壞或教師四狀態變化。**修改任何共用R文字、客觀後果或必要前提後，重新判定完整32格**，不強迫改動原本仍合理的值，也不重新抽教師四狀態 | 04第5區完整4×8權重與每個0的客觀理由；正式驗收紀錄留**每一格的相容性、因果方向、具體依據、權重、既成行動是否保留**，不能只寫「可能發生」 | 因果不通先辨識客觀互斥、敘事跳接或他人自主行動；不可把低機率硬判0，也不可把真不可能硬填1。若同一R依賴單一選項而導致超額0，先修共用R而非湊合法數字；修稿後**全32格重新判定、僅變更因果確有改變的值**。驗收以一次完整判定及交叉檢查為原則，只有具體新證據或修稿才複查，不做無限重配 |
| **9 機械＋GPT內容驗收** | 依序執行`summary／choices／full`機械檢查；GPT依05七項契約審查臺灣私校情境、人物與四碼資格、選項、八結果、32格、日期與法律、V3數值、NPC逐碼因果及跨批摘要／全文查重，保留可對照的七項證據、六選三及每項NPC警示判定。**集中反查三種公式化**：①人物數量／身分／對立是否由劇情而非慣用模板產生；②情緒行動是否由可信心理驅動而非刻意做錯；③核心困境、人物作用及教師決策是否與既有篇真正不同。合理的重複不設配額；不靠添人、換字母、改情緒名稱過關；機械pass≠內容approved | 通過的五區塊Markdown、只讀機械報告、依05保留的正式驗收證據 | 依05退回相應摘要／人物／選項／結果與矩陣部分並重驗受影響階段；**數值與劇情只針對明顯缺乏增減因果的R局部改一次**，不因主觀文采反覆改寫；NPC警示須具體處理；只換皮則重構摘要；不為不通過而重跑全部不相干檢查 |
| **10 正式驗收** | 依05與06核對機械檢查、GPT審查、種子唯一性與配額 | 記錄正式ID、所審Git版本及驗收結果 | 原檔修訂，再審受影響範圍；日常預覽持續可用 |

### 重要：不要把「文件已說明」當作「工具已檢查」

- 稿件檢查器要求A～D恰一個情緒選項。正式驗收工具可檢查六普通候選、三個中選ID、A～D映射和正文情緒標記。隨機過程及候選的實質差異由GPT審查。
- T稿的 `required_window` 填池ID，Markdown 的 `quota_date` 填獨立的配額歸屬日。池內日期及正式校曆資格可由工具查詢，故事當下的知情與在場仍須審查。
- `4／2／1／0`的零上限是**V1稿件硬性門檻**，4：2：1仍待正式遊戲平衡；數值限額（底層單R−8～+8、四狀態依05的V3五組配置，NPC八R平均±3已取消、四狀態固定−0.5）是機械稿件試作限制，**不能冒充已驗證三年通關率**。
- 正式驗收保留七項證據、六選三、32格因果及NPC警示複查。測試資料放在故事目錄之外。

## 四、GPT最少閱讀與實際交付格式

**開始一篇前**：讀本檔（03）、[04範本](./04-五區塊故事稿範本.md)；需要人物資格時查[01](./01-人物數值與四碼資格.md)，日期／T主題查[02](./02-事件分類與時間資格.md)及唯一T20表。只在**涉及查重、種子占用或正式驗收**時參照[06工具說明](./06-種子與量產管理.md)；內容退件按[05](./05-故事品質與驗收契約.md)。

**逐篇創作的三個檢查階段**（同一份正式 Markdown 的逐步完成）：

- **摘要版**：04第1＋2區，附同批／跨批疑似重複候選的具體比對；使用同一正式 ID 保存與預覽。
- **選項版**：補第3＋4區，填入原四碼，交最終四行動；六個普通候選短句及中選三個編號放**獨立審查紀錄**而非五區塊正文。
- **完整版**：補第5區八共用R與矩陣、執行全部數值及內容審查；依05獨立完成正式驗收，之後可沿用原 ID 與種子修訂。

**避免重工的修稿原則**：摘要不合法只動第1／2區；角色或種子不合先檢查第一區種子與第三區角色，並確認是否影響摘要；四選項重複只修第4區，且重新核對受影響的全部8格；一個R明顯缺因果先局部修該R；**若任何共用R有修改，即須重新判定完整4×8權重矩陣**，但只實際改動受影響數字，不必整篇重寫；矩陣數學不合法必須在寫R前排除，避免寫完再回頭換數值；若核心困境已被證明換皮，則**必須回到摘要重構**，不得靠換人名、加對話或小改字數矇混。

## 五、固定範本欄位與檢查指令（不可擅改）

以下命令是**現有工具**，不是新建的正式故事轉JSON工具；檔案路徑是使用者自行建立的稿件位置：

```bash
npm run content:draft-check -- --input work/your-story.md --stage summary
npm run content:draft-check -- --input work/your-story.md --stage choices
npm run content:draft-check -- --input work/your-story.md --stage full
node scripts/story-state-matrix.mjs # 先產生四組不重複的合法32格，之後再撰寫R
npm run content:production -- status
npm run content:production -- audit T1-001
```

- **不修改04的固定區塊標題／表頭／矩陣識別**，直到同步修改並驗收`scripts/story-draft-validator.js`及其定向測試。原可填範本已於第06批轉入04；**它是撰稿Markdown契約，尚不是正式JSON Schema、轉檔器、角色替換器或遊戲引擎**。
- `story_id` 填正式 ID，檔名相同。Git 推送後等 Pages 發布，再重新整理閱讀器。
- 正式驗收時，GPT須留存32格敘事因果、跨庫查重、動態人物在場與知情、日期與情節合理性，以及六選三過程的審查證據。
