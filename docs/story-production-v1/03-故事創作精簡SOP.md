# 《教師荒謬地獄》正式故事 AVG 演出製作 SOP

> **現行工作入口**：以實際可讀取的正式故事為準，統一製作人物、表情、姿勢、背景及音樂。所有故事依同一套演出流程處理。格式見 [04](./04-五區塊故事稿範本.md)，品質驗收見 [05](./05-故事品質與驗收契約.md)。

## 一、工作範圍與資料來源

- 第一階段為已發布的 **T1-001～T1-060 共 60 篇**，往後故事直接沿用相同作業流程。
- 閱讀來源為 GitHub Pages `gh-pages` 的 `stories/data/index.json` 與 `stories/data/stories/<storyId>.json`。先確認每篇實際有 `storyId`、`title`、`summary`、`opening`、`options`、`results`、`matrix`、`sourceMarkdown`；缺少的資料如實回報。
- 只編排**演出**：合法場景、說話者、人物進退場、學生表情、成人姿勢、必要的畫面呈現形式與每篇唯一配樂。原有故事敘述、四個選項、八個結果、數值與 4×8 矩陣保持不變；遇到正文矛盾先記錄，不藉演出施工自行改寫故事。
- 現有正式故事試演能讀取發布 detail 的 `music` 及 `sourceMarkdown` 裡的 `avg` 標記；**產生標記不等於自動發布**。新資料須透過實際已驗證的發布程序寫入可讀取的 detail。正式遊戲事件引擎的內容來源需另外核對，不能以試演成功代替。

## 二、每篇故事固定六步

| 步驟 | 施工動作 | 完成標準 |
|---|---|---|
| **1 讀取全文** | 讀主題與四欄摘要、每頁 P 開場、A～D、八種 R 結果、已定義角色槽位、合法日期與活動情境 | 能逐頁列出發言者、場景、在場人物與必要的劇情變化 |
| **2 編排場景與登退場** | 逐頁判斷位置與誰在場，使用合法 `scene`、`speaker`、`enter`、`exit`；新人物進場前先清出位置 | 教師是玩家第一人稱，同幕最多兩位 NPC，人物身分及知情狀態合理 |
| **3 編排表情與姿勢** | 學生用六種既有表情，成人用六種既有姿勢，依台詞與關係變化安排；情緒連續時保留前頁狀態 | 變化自然、不強迫每頁換表情，不改 UI-2 站位、身高、服裝與比例 |
| **4 指定事件音樂** | 依故事主題、四欄摘要與主導氣氛，從七首音樂選**唯一一首** | `music` 為事件層級，不放在 P 頁與 R 結果；選項及結果期間全程同曲 |
| **5 檢查 R1～R8** | 每種結果各自從**相同開場結束狀態**建立演出，檢查說話者、進退場、情緒與場景 | 八種結果互不串場、不繼承另一個 R 的狀態；原結果文字完全相同 |
| **6 驗收及發布** | 使用既有驗證器與開發測試中心核對標記、人物、畫面、配樂、全部選項及結果；確認發布版本確實讀到編排 | 標記合法、內容一致、試演可讀取、畫面可驗證，分別記錄結果 |

## 三、演出判斷原則

### 角色與鏡頭

- `teacher` 不以第三人稱立繪出現；玩家以導師視角閱讀。
- 常駐角色只使用故事實際存在的合法槽位鍵，不能替沒有資料的文字角色杜撰永久姓名、ID、立繪或數值。讀取故事第 3 區角色槽位對照後才使用人物呼叫。
- 每幕最多兩位 NPC；退場只影響畫面、不會把角色從故事中刪掉。同頁需要換人時先 `exit` 再 `enter`。
- 同一人物在合理連續情境可跨頁維持原表情／姿勢。每次明顯變化須有劇情依據。成人與學生使用不同的既有畫面配置。
- 校曆與活動決定制服、運動服或便服；場景使用現有合法場景鍵，禁止新增臨時場景名、繪圖方法或第二套人物渲染。
- 電話、通訊、公告、電子郵件與新聞頁視既有 `presentation` 格式處理，不強迫每一行文字都出現人物。

### 八結果與選項

- P 頁按原始順序演出；A～D 只執行原本四個選項，沒有第五個選項或新的結算。
- 每個 R 都以同一開場終點為初始狀態，獨立渲染；不要因為先看過 R1，導致 R2 保留 R1 的人物或場景。
- 若 R 的台詞需要不同人物或地點，僅在該 R 加入必要標記。切換結果、退回開場或重新進入應呈現一致。

### 七首音樂

| 代碼 | 氣氛 |
|---|---|
| `school` | 一般校園、普通校務 |
| `conflict` | 人際爭執、衝突 |
| `serious` | 危機、重大壓力或嚴肅抉擇 |
| `home` | 居家、私人日常 |
| `playful` | 輕鬆活動、遊玩 |
| `touching` | 感謝、和解、溫暖感動 |
| `absurd` | 荒謬、諷刺、哭笑不得 |

- 不依單句關鍵字、人物當頁表情或 T／G／P 類型選曲；以整篇主要氣氛優先於地點。七首不必平均分配。
- 事件從開場到選項及 R 結束，維持同一首。事件外依當下活動與場景選曲：一般校園 `school`、在家 `home`、校慶等活動 `playful`、畢業典禮 `touching`；事件結束回到**當下情境**的配樂。相同歌曲不重新開始。

## 四、交付、品質檢查與批次作業

**每篇工作紀錄**只保留必要資訊：`storyId`、讀取的發布來源、事件音樂、標記是否完整、P 頁與八個 R 是否可試演、原內容有無變動、畫面／音樂實測狀態及待修問題。不建立額外演出管理系統。

**驗收順序**：先檢查解析與代碼；再檢查人物最多兩位、場景、進退場及八結果；最後以正式試演核對實際發布資料。先修有問題的頁面／結果，再執行相關定向測試。不要重跑無關的大型模擬。

**前 60 篇的開始條件**：先以 3～5 篇不同氣氛的故事驗證既有發布程序是否能讓正式試演載入標記及配樂，並核對正式遊戲資源的接線方式。這屬於同一套 SOP 的小樣驗證，不是另一種稿件種類。流程確認後，以相同格式完成 60 篇。

**完成狀態分明**：已編排 ≠ 已發布 ≠ 已實測；只有內容一致、標記合法、試演讀得到且實際畫面檢查通過，才可標為「AVG 演出完成」。不能因示範劇情成功、GitHub Actions 成功或文件撰寫完成就把 60 篇列為完工。
