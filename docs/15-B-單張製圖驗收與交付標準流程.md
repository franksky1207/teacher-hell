# 第 15-B 批｜單張美術製作、驗收與交付標準流程（SOP）

> 本文件整理 **student-001 第一張人物母圖**實際反覆修正後確認較有效率的工作方式。以 [B1～B23 美術規範](./15-B-正式美術原型規範.md) 為美術標準，以 [素材命名與製作進度簿](./15-B-美術素材命名與製作進度簿.md) 為唯一進度依據。
>
> **目標：一次製圖、技術修正與驗收由助理完成、一次交付；只在必要的美術方向與關鍵母圖核准時請使用者決定。**
>
> 本流程不使用 Codex、不得自行合併 main／部署；本文件屬流程規範，不代表任一圖片已完成分層或可上線。

## 一、第一張圖的實際教訓：哪些做法不要再重複

1. **不可先製作拼版概念圖當正式素材**：第一輪把多名學生、六表情、服裝與驗收表畫在同一張圖片，導致無法獨立使用、沒有透明可替換圖層，圖上的「通過」也非真正檢查證據。
2. **不能只看圖片表面就說合格**：即使看似透明，邊緣可能有光暈或低 Alpha 殘留；不能只憑圖檔副檔名或四角透明就宣稱完整驗證。
3. **第一張人物下緣構圖必須先確定**：舊圖人物與裙襬碰到畫布底部，不利於部分顯示方式。新版採**完整裙襬入鏡、腿腳可以不顯示**，人物上下保留透明空間。此為第一位原型的已選方向；其他相容立繪須守相同可見比例與錨點，不是只要求全員一定有裙子。
4. **不能每次修改都重畫整名人物**：如果只是清除透明背景光暈，直接修正**同一圖檔的 Alpha 通道**，保留人物原本的 RGB、五官與制服；重繪可能產生換臉、身形與校徽變形。
5. **後製只能修復可修復的問題**：小幅透明邊、對齊、壓縮可以處理；角色五官走樣、服裝錯誤、構圖不良與真正缺圖層，不能用文字聲稱後製完成。
6. **不要讓使用者做可由助理完成的技術工作**：不要反覆要求確認去光暈、尺寸、透明度、改名、哪個資料夾；應由助理處理完再一次交付。
7. **不可以因為上傳或檔名存在就宣告正式核准**：GitHub 檔案與使用者美術核准是不同事情；圖片是平面 PNG 也不等於分層驗證已通過。

## 二、每次製圖前：先讀、先定名、只做一張

1. 讀取第15批**目前開發分支**的進度簿及 B1～B23 規範，核對 GitHub tree 的上次檔案路徑、大小與狀態。不可憑前一段對話記憶跳號。
2. 確定這次唯一的資產 ID、角色母圖及**最終交付檔名**，例如 `student-001-base.png`，下一張表情例 `student-001-expression-happy.png`。產出前先決定正確資料夾及手機／桌機需求。
3. 先確認畫布：人物目前試驗基準 `1024×1536`，手機與桌機人物共用透明母圖；背景則以相同 scene ID 的桌機橫式、手機直式兩張**獨立構圖**製作，嚴禁裁切取巧。各尺寸尚未經完整原型驗收封版。
4. 每次圖片生成**只能是一名人物／一種表情／一套服裝部件／一個獨立背景**；禁止表情六宮格、多人物合照、文字說明面板、驗收打勾標籤、水印。驗收結果記在文字文件，不畫進圖片。
5. 若是既有人物的新表情／服裝，必須以**目前已核准的母圖**當實際參考，不可憑文字重新猜同一張臉。若圖片工具仍使身形／錨點改變，視為待修，不能假稱可無縫切換。

## 三、生成後由助理一次完成的精準驗收

依素材種類採用相應項目，不為純文件修改或未涉及的遊戲系統跑大型測試：

| 類別 | 必檢項目 | 未通過時處理 |
|---|---|---|
| 檔案基礎 | 實際像素尺寸、PNG/WebP 格式、透明通道、檔案完整性 | 自行修正／重輸出，不請使用者選技術項 |
| 角色外觀 | 畫風、臺灣私校制服、單人、自然正面、髮型、五官與校徽辨識 | 影響設計方向時才請使用者核准 |
| 畫布／構圖 | 人物中心線、眼線、肩線、可見比例與錨點；裙襬完整、非刻意截斷 | 基準未定就先修；不帶錯誤去製六表情 |
| 透明與邊緣 | 四角透明、背景有無殘影與低 Alpha 光暈；明／暗背景下的髮絲及衣服邊緣 | 優先修**原圖 Alpha**，確保人物不換臉 |
| 表情／換裝 | 同一角色可替換圖層的尺寸／相對定位一致，必要時像素級比較；不可把平面圖當可換裝圖層 | 不符就留在候選階段 |
| 手機／桌機 | 人物同素材雙版面與文字框、兩人同場；背景兩套獨立構圖同一場景 | 原型顯示未驗證就不宣稱已上線 |
| 資源權利／紀錄 | ID、檔名、實際路徑、授權／來源、SHA（若可取得）、核准狀態 | 如實標示未確認，不填虛假通過 |

重要：Alpha 門檻 `≤20` 只是**本次第一張清理所採用的參考值**，不是全人物固定強制門檻；後續需避免誤刪真正半透明髮絲。正式檢查依實際畫面與邊緣品質。

## 四、第一張 student-001 的經驗數據（只供案例，不套用到每張）

- 原候選圖 `student-001-base.png`：1024×1536 PNG RGBA，1,229,375 bytes；人物下緣碰到畫布底部。
- 修正版保留相同學生外觀，重新安排構圖使裙襬完整、腳部不必入鏡，人物周圍留白。
- 對**同一張修正版**做透明通道清理：將 Alpha≤20 的 22,382 個低透明度殘留像素清零；高於門檻的可見人物像素未修改。
- 交付清理後的 `student-001-base.png`：1024×1536 PNG RGBA、1,577,550 bytes；既有對話記錄 SHA-256 `2969c4ab6a07d6e09d3f584b1cfe319bff167e8cf49d3c3f18338654a97bea11`。
- 此例是「較好的處理流程」，**不是**正式核准或遊戲整合的證明。新構圖比舊版合適，不代表六表情及服裝分層已完成。
- 若同名 PNG 上傳 GitHub，需再核對 Git blob／必要時取回解碼；**檔案大小相同不足以證明 SHA-256 相同**。

## 五、一次交付、一次上傳、一次紀錄

1. 把所有可自行處理的技術修正完成後，直接將下載檔**存成規格要求的最終檔名**，例如 `student-001-base.png`；不交付 `final.png`、`版本2.png` 讓使用者改名。
2. 在**同一則回覆**提供：圖片下載連結、GitHub **目標資料夾的開發分支直達連結**、簡短驗收結果及仍待處理的限制。若是同名替換，明確說「取代同名舊檔」。
3. GitHub 連線能取得完整圖片位元組時可直接上傳；若工具間無法傳遞 PNG，就由使用者透過 GitHub 網頁上傳。不得宣稱自己已上傳未實際入庫的圖片。
4. 使用者上傳後，再核對 GitHub tree：路徑、大小、Git blob SHA；必要時和已知原圖雜湊比對。接著更新進度簿的**實際張數、狀態與下一張唯一檔名**。
5. 關鍵人物／制服／成人剪影／第一組背景由使用者**一次核准美術方向**；一般技術修補與後續沿用母圖的合規素材由助理自檢，不為每個小修正反覆提問。
6. 母圖核准 `master-approved`、表情分層已通過、網頁正式接線 `integrated` 是**不同階段**，不可混寫。
7. 無須為純素材命名／進度文字修改跑全部 CI、三年模擬或大型瀏覽器回歸；只有開始真正接線後才做對應的精準測試。

## 六、穩定交付格式（精簡）

- **目標**：ID、唯一檔名、素材用途。
- **檢查**：通過／待修的實際項目，不把「肉眼看起來合理」當程式驗收。
- **交付**：同名可直接上傳的檔案＋開發分支資料夾直接網址。
- **紀錄**：GitHub 是否有檔、用戶是否核准、下一張做什麼。
- **例外**：只有關鍵造型改動或無法自行修復的品質問題才請使用者決定。

此 SOP 的後續修訂應同時維護進度簿與素材 README 的連結，不另建彼此衝突的第二套美術規則。

## 七、表情自然度驗收修正（2026-11-07）

> 根據使用者否決 `student-001` 的 happy／surprised 兩張表情圖：**只換嘴巴、保持其他像素原樣不是可接受的表情製作法。** 先前兩圖均不得計入通過或正式資產。

1. 人物身份要一致（臉型骨架、五官基本辨識、髮型、服裝、姿勢與畫布錨點），**但表情所需的眉毛、眼睛、眼瞼、嘴型、臉頰及細微臉部線條允許同步變化**；不要限制成固定幾十像素的嘴貼片。
2. 製作優先使用既有母圖的臉部區域編修，檢查整體神情是否自然；若不自然即淘汰，不能因透明通道一致、差異像素很少而視為合格。
3. 確認人物仍是同一張臉、姿勢及制服，避免工具把髮飾、衣服、眼睛顏色一起改掉；必要時調整工具流程，不盲目反覆生成。
4. **驗收先美術自然度，後技術規格**。工具無法達成時如實記錄，禁止提交看起來僵硬但技術條件通過的表情圖。
5. 失敗檔保留 Git 歷史供問題追蹤即可，進度簿標示 rejected；不再提供已被否決的圖作正式交付。

## 八、使用者說「好了」的固定交接規則（2026-11-07）

- 使用者說「好了」代表剛才交付的圖檔已由使用者上傳；**第一步直接查 GitHub 指定開發分支**，以路徑、大小及 blob SHA 等實際資訊核對，不能只憑口頭聲稱完成。
- 技術驗證透過程式及 GitHub 資訊完成；可核對尺寸、Alpha、畫布、錨點、參考母圖差異與檔案完整性。**不要為了核對而呼叫圖片生成工具**。
- **嚴禁產生或呈現驗證圖、比較拼版、統計資訊圖、圖上勾選清單**。若使用者沒有特別要求，也不用顯示放大檢查截圖；結果以簡短文字回報。
- 更新唯一美術進度簿後直接進入下一張實際圖片製作，僅顯示／交付單一角色素材，不用重新解釋已完成的流程。
- 自動驗證不能取代角色自然度與情緒辨識的美術檢查；已接受的素材不等於分層／遊戲執行已完成。
