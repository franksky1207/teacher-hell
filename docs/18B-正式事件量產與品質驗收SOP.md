# 第18-B｜正式事件量產與品質驗收 SOP

> **狀態：2026-11-15 修訂版；適用第18批試產及後續量產。** 本文件整合原「18-B 正式事件量產工作流程」及 T10-03 第一次試產發現的問題。這是**批次製作、品質審查與放行規則**，不是新事件引擎。每則事件的資料契約與細節仍以 [17-D 正式小事件製作與驗收 SOP](17D-事件內容量產SOP.md) 為準；自動檢查的操作以 [18-A 事件量產工具規範](18A-事件量產工具使用規範.md) 為準。與兩者衝突時，先查現行引擎並提出具體衝突，不擅自修改核心規則。

## 一、目標與不可變原則

- 正式庫為 **128 主題 × 每主題至少20則真正不同的小事件（基本至少2,560則）**，**20是下限，不設上限**。同故事不同選項、variants、換人名、日期或布景都不能額外計件。
- **最高原則：同事件、同選項仍可因已知人物特質、歷史、關係、教師狀態及合法權重，出現多個合理而且可追溯的結果。** 不可變成「選A固定成功／選B固定失敗」；也不可為了隨機而任意反轉。部分簡單選項可以只有單一結果，不能強制每個選項都塞多結果。
- 臺灣高中真實作息、制度與公開資料用來研究題材與權責，劇情人物與事件自行虛構；**未經查證的指控不得寫成遊戲中的既成事實**。一般日常、正向、荒謬、負面、長期困境都可自然存在，不設各類固定配額。
- 嚴守現有 17-D 四選項、自然情緒選項、資格替換、合法畫面、知情邊界、歷史與後續契約；不更動 N1～N8、K、事件配額、年資難度、校曆、存檔、曝光或事件引擎，不建立平行結算器。
- 40位學生需要公平的**實質互動機會**，不是強制輪流登場，更不能以危機灌曝光。試產內容預設**不進正式池**，未經明確放行不轉成 ready 或正式上架。

## 二、先骨架、再劇情的七個步驟

以下是**同一批的工作順序**，不是每個步驟都要獨立PR、跑大型驗收或等待使用者批准。

1. **選主題及查找題材**：讀取 GitHub 最新 T 主題、17-D、現有已接受事件登記簿；參考臺灣學校情境、法規與可核對的研究。標明來源、推論、虛構。不要為測試而虛稱資料出自新聞。
2. **建立事件骨架清單，先期去重**：每個候選記錄主題碼、暫定ID、客觀起因、教師實際職責、已知／未知與知情來源、人物與時段資格、主要策略、可成立的後果及和同／跨主題已接受事件的**實質差異**。骨架相同先合併或改寫，**未通過骨架去重不可直接展開成大量正式劇情**。
3. **獨立設計因果與人物差異**：先依故事個別決定可見資訊、當事人動機是否仍未知、四種實質不同且合法的導師策略、哪些結果受關係／歷史／能力／不確定性影響。使用既有 `variants`、合法權重與必要的 `requires`，避免固定機率套版。分支後果要**實際不同**，僅換文字不算不同結果。
4. **寫成正式資料**：依17-D填入逐頁臺灣校園文字、可觀察反應、合法場景、四選項、數值／事實／主張／歷史／後續，並與候選定義一致。**劇情長短、角色數、場景、節奏及是否跨日由事件內容決定**；不得所有事件都強制兩頁、同四策略、同單階段或同結局。單純日常也不必硬寫多階段。
5. **精準結構檢查**：用既有 `validateStory`、`validateEventDefinitions` 與18-A檢查器驗結構、合法資格、版本、重複候選、多結果等價預警。工具字串相似度只是提示；**程式檢查通過不等於語意品質通過**。錯誤只修相關事件，必要時再做單一事件／核心相容測試。
6. **獨立AI劇情審查及修正**：以和撰稿不同的審稿流程逐則審查真實感、已知事實與傳聞、臺灣制度及權限、四選項差異、同選項多結果因果、人物與時間、連鎖合理性、跨篇換皮。紀錄**具體ID、問題、修改、再審結果**，不得只填 `approved` 或一句空泛理由來冒充審查。校安、霸凌、性平、身心危機等需額外程序查核；審稿未完成即待審。
7. **批次遊玩體驗審查及存檔**：對照累積內容，統計起因、教師策略、結果類型、人物／年級、正負基調、故事長短、單日／跨日、時段與場景的重複情形；注意連續玩法是否都像在選相同四句、是否所有結果只差一個數值。**不硬性配額，不以此取代第21批正式平衡與三難度驗證**。保存審查證據和下一批可比對的 baseline。

## 三、第一輪 T10-03 試產的失敗教訓（不得重犯）

- 首次 PR #60 測試資料有20個不同起因與四個選項，但大量使用相同兩頁、同場景、單階段、相似策略與結果模板。**格式看似整齊≠故事多元**。再測試時沿用20個已有骨架，**逐則決定真正必要的改動**，不為多階段而多階段、不整批重做。
- 先前測試先建立了測試案例，卻未拿到該 PR 最終專項 CI 的完成證據。**測試檔存在≠測試通過**。每次報告必須分清已寫、已執行、通過、失敗、未觸發、未驗證；CI沒有觸發時可使用可核對的等價精準命令，但沒有實際執行就明確註記未驗。
- 即使20則結構合法、具有 variants，也不能宣稱人物歷史、跨日後續、存讀與不同策略皆已測過；**覆蓋範圍須按實際案例逐項列出**。代表性多階段、人物條件與結果差異可在適合的事件中測試，不強迫所有事件使用同結構。
- 第一輪品質審查明確指出模板化，故 PR #60 **尚未通過完整語意／玩法品質驗收**；不得由 authored 20 直接推論正式庫完成20或已有20則可上架。

## 四、測試身份與放行門檻

**測試批：** 用 `engineering-test` 與 `engineering:` ID，留在隔離測試資料或非正式資源；不註冊進正式候選池、不得誤設 `ready`、不進玩家新生涯、不計正式上架。測試通過只是工作流程與樣本合格，**不代表自動轉正**。

**量產正式批：** 逐則保存主題、唯一資源／定義ID、版本、來源、骨架、狀態及必要候選資格。以資料狀態區分：
- `authored`：已撰稿（包含未完成／未審，不能當合格數）。
- `structurallyValid`：實際執行結構檢查通過。
- `reviewed`：具體AI語意審查紀錄已完成；這是審查紀錄，不代表絕對正確。
- `resolverReady`／`catalogueReady`：正式資源解析與目錄接線已驗證。
- `publishedInNewCareers`：另經真正新生涯合法抽選／接入證明，否則維持 `not-assessed`。

**可判定單主題試產驗收通過的最低條件：** 20則以上實質不同的起因；每則符合既有資料契約、基本四選項與合法結果；完成具體、可追溯的AI語意審查與跨篇去重；批次代表案例實際驗證加權多結果、人物條件（如適用）、長短或後續變化（如有）；必要精準測試有可核對結果；測試內容仍隔離且不宣稱正式上架。若有未完成項目，狀態只能是**需修正／未驗證**，不得整批宣告成功。

## 五、測試與 GitHub 成本規則

- 先執行**本批專項、單一事件／內容契約**檢查；錯誤定位後只修受影響的檔案與事件，重跑必要範圍。**不得為驗一批內容而反覆跑三年／30年模擬、完整瀏覽器矩陣或全部歷史回歸**。
- 不把 CI 未觸發當作通過，也不為了觸發 Actions 而任意調整正式分支。要驗證時，先確認 workflow 的觸發條件及目標分支；用既有精準命令或經確認的最小工作流程，明確回報證據。
- 每批回報：新增／修正事件數、語意退稿與具體修正數、可能重複清單、結構檢查執行結果、尚未覆蓋的功能、GitHub PR／分支、正式上架狀態。使用者不必逐篇驗收。
- 不自行合併、部署或將測試資料轉正。只有內容可驗證、技術驗證通過且經使用者授權時才做對應操作。
- ChatGPT 與 Codex 使用**相同規格與驗收條件**。先比較實際完成品質、修正次數、審稿成本與可查的用量再決定分工；不憑空宣稱哪一個比較省。Codex若用，只負責指定批次及精準修正，不自行擴張工作範圍。

## 六、跨批去重操作與限制

```bash
node scripts/audit-content.mjs --input work/new-batch.json --baseline work/previous-batches.json --output work/new-batch-report.json
```

- `--baseline` 使用**累積所有已接受事件**的靜態紀錄（陣列或 `{records:[...]}`），只做舊批對新批的疑似重複比對，不將舊批事件加進本批完成數；同批事件也互相比對。
- 字面不相似仍可能同質，AI須比對「成因、教師職責、資訊差異、四選項策略、後續因果」；有疑慮先標待審，不由相似度自動刪除。
- baseline不會由CLI自行下載 GitHub，也不會自行保證全庫內容完整；製作者要明確提供其來源與範圍。
