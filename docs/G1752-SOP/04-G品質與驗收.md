# G1752 專屬 SOP｜04 階段檢查、完整驗收與雙預覽交付

> **適用G四選四與三階段橫向製作**。T的八個R、4×8權重、V3及相應審查不適用。故事真相只有一份正式G Markdown；內容、AVG、驗收證據、兩個公開頁面必須同版本。**新批次須於階段三完成24篇整批核准並獲授權才晉升；已發布故事的後續修稿可按授權單篇晉升與更新，不等下一批。**

## 一、三階段品質檢查與最終完整驗收

不在三個階段各做一次完整故事驗收，而是依當前階段執行必要的階段性檢查，最後於階段三完成全篇完整驗收：

| 階段 | 檢查重點（保留每篇必要品質把關） |
|---|---|
| **階段一（開場與選項）** | 合法日型／觸發時段／年級／在籍／知情／場景時間一致（含G11時間界線）；固定種子與四碼合法持有人；自然開場與選擇前對話；六普通＋一情緒候選及真實隨機洗牌證據；四行動各具不同已完成事實與實質代價（安全／法律／查證／權責必要程序不作選項）；四條「後果可行方向」成立。 |
| **階段二（結局與數值）** | A→R1至D→R4延續對應已完成行動與知情事實；各R至少一項可區別的實際事實或關係變化；人物自主反應合理；各R採用58庫中合法且同篇互異的四狀態；原固定四碼合法NPC／玩家非零增減（NPC每碼每R介於−8～+8）具真實故事理由；不出現R5～R8或權重矩陣。 |
| **階段三（AVG與完整驗收）** | 全篇無`【待填】`佔位；唯一AVG JSON合法；合法speaker、scene、enter/exit、expression、pose、presentation、音樂與同場最多兩NPC；四R各自獨立；開場與結果可見內容、行動及事實與原稿一致，不洩漏技術JSON；跨批獨特性確認無換皮及整批異常縮水。 |

### 敘事篇幅彈性參考（非硬性驗收門檻）

- **T648九篇抽樣參考**：既有九篇T事件抽樣之開場平均約162字、每個結果平均約149字（**此為九篇抽樣，非T648全庫統計，不得冒稱全庫結果**）。
- **G1752彈性參考**：開場約**140～200字**、每個R約**140～200字**；情緒鋪陳較多者可自然延伸至**220～250字**，簡單日常或幽默故事可更短。不為字數灌水，亦不將開場或結果縮成摘要。
- AVG分頁依自然對話節奏決定，不固定頁數，不讓角色朗讀旁白。可用程式統計每24篇玩家可見文字長度，發現整批異常縮水時才定向抽查，不要求每篇另做一次字數驗收。

機械驗證器必須依階段檢查[03格式](./03-G五區塊範本.md)、四碼映射、四選四／58庫、AVG、可見正文與正式JSON，證據須標明故事ID及來源版本。**機械通過不能代替語意驗收。** G驗證器、G匯出器及兩種試演的支援尚待工程實作；不可宣稱已通過。

## 二、批次資料、驗收紀錄與定向回修

- 每批24篇在`content/events-v1/G/Gxxxx-Gyyyy/`規劃及創作；正式故事檔名`Gxxxx.md`。規劃MD與階段一、二工作草稿不計入已核准故事。
- 批次下`驗收紀錄/evidence/Gxxxx.json`每篇一份，記錄該篇階段完成狀態、六選三抽選、四條後果可行方向、四R因果、非零數值理由、審查版本及實際結果；階段三另維護**唯一一份**`驗收紀錄/Gxxxx-Gyyyy-批次驗收報告.md`，**不再另外堆疊多輪歷史審查文件**。
- **定向回修原則**：若在階段二或階段三發現前一階段存在真正缺陷，只定向回修受影響的摘要、開場、選項、結果或AVG；若修改候選池或最終選項，須依原隨機規則重新取得並保存抽選證據，並核對A～D與下游R及AVG的映射。**不因一篇故事有問題而重新審查同批其他23篇。**
- 階段三一批24篇全部具備合法故事、原文／AVG一致、審查證據及必要測試後，才可取得**使用者授權**一次晉升正式V1；草稿自驗、PR或CI成功都不等於已發布。
- 核准晉升時依[06](./06-T648固定標籤基準與G動態統計.md)計入本批24篇最終有效標籤，原位更新索引及預估差額；階段一、二草稿標籤不得提前入正式帳本。

## 三、兩個正式預覽介面：首次發布及修稿都同步

| 介面 | 唯一入口與可驗證內容 |
|---|---|
| 故事全文預覽／閱讀器 | `https://franksky1207.github.io/teacher-hell/stories/`：搜尋G ID／標題、閱讀原稿／四選項／R1～R4及最新版內容 |
| 測試中心 AVG | `https://franksky1207.github.io/teacher-hell/preview/` → 測試中心 → AVG → G通用：依24篇批次選故事，觀看開場分頁、四行動及對應四R演出，含人物、表情、場景、特殊介面及音樂 |

**工程硬門檻（依階段對應，階段三正式發布前須備齊）**：原`scripts/story-catalog.js`、`web/story-performance-preview.js`仍部分使用舊`G-0001`ID；`scripts/export-story-reader.mjs`目前只解析T八R和權重；`web/story-preview-picker.js`以50篇分組。須於階段三正式驗收前讓兩介面及匯出器支援正式`G0001`～`G1752`與**G獨立四結果契約**，G選單依24篇批次，T/P保留既有行為。只選取**正式已完整發布**的故事，不能把規劃MD或階段一／二草稿當故事。

**共用唯一來源與發布流程**：
1. G正式來源僅為經核准的`content/events-v1/G/…/Gxxxx.md`；只從該來源**產生**故事索引與單篇JSON，嚴禁直接手改`gh-pages/stories/data/`或複製第二份AVG故事稿。
2. **新批次**：階段三24篇核准、獲授權晉升V1 → 重新匯出故事資料並部署 → 確認兩介面均有24篇且同一來源版本，故事全文可讀、AVG可播放四選四。
3. **已發布故事任何修稿**（標題、開場、選項、結局、數值、標籤、AVG台詞、立繪、場景、音樂等）：修改原Markdown及受影響驗收證據、複驗並獲授權晉升 → **立即重新匯出並發布兩處所需的故事資料**；不等下一個24篇批次。只改內容毋須無意義重建前端，但兩介面仍必須讀到最新資料；若改編譯器／UI／素材則另部署必要前端資源。
4. **版本核對**：故事索引、單篇JSON、發布記錄使用同一已核准來源版本；兩個公開頁都要實際開啟核對（含快取問題），只要一處仍舊版就算**本次預覽同步未交付**，不得冒稱成功。驗證已核准修稿的受影響頁與對應R即可；新批次查全部24篇。更動共用程式時只做必要T代表篇回歸測試，不重驗T648。

## 四、修稿／版本與交付狀態

- **原稿修正**：只重驗受影響段落、選項、R、數值及AVG；若改教師客觀行動則重驗對應固定R；不因改一篇而重做整批或T648。新證據要對應新來源，不得沿用舊SHA冒稱現稿通過。
- **標籤入帳**：階段三24篇首次核准後依[06](./06-T648固定標籤基準與G動態統計.md)新增一次；已發布故事修訂若標籤變動，**替換原批次該篇標籤及證據版本，按新舊標籤差額增量更新正式累計與預估累計**，絕不增加已驗收篇數；標籤不變則不重新統計。完整重算僅依06例外條件。
- **交付狀態**：S1開場／選項與四R完成、S2語意／因果／數值核准、S3 AVG完成、S4編譯與定向驗證、**S5已授權發布且故事閱讀頁＋AVG均實際呈現相同最新版**、S6正式遊戲引擎／存檔／結算（另行授權）。階段一、二草稿及S1～S4不得冒稱S5或S6。
- **橫向階段與S狀態分開記錄**：階段一完成僅表示開場、選項與抽選證據通過本階段檢查，**不等於S1**；階段二完成表示四R及數值草稿補齊並通過本階段檢查，只有符合原有S1、S2各自條件時才可對應標示，不能直接視為正式故事核准；階段三須依實際完成的AVG、編譯驗證及授權發布分別確認S3～S5。工作草稿的階段完成狀態記於既有`evidence/Gxxxx.json`，S狀態仍遵照本節定義，不新增第二套交付狀態或因階段完成而提前晉升V1。
