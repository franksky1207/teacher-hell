# 第18-A｜事件內容量產檢查器試產規範

## 目標與不可變更原則

- 正式內容規劃為**128個T主題，每個主題20則「實質不同的小事件」是下限而非上限**。允許且鼓勵依臺灣現實校園議題、民間與官方資料持續增加，無每主題或總量的硬上限。新聞的指控與統計不等於遊戲人物已經做過的事；公開資料只能用來研究情境、責任與制度邊界，故事人物、事件及具體細節應自行虛構，不以未查證素材作為劇情事實。
- **最高原則**：同一事件、同一個選項仍可能產生不同的*合理*後果；依老師、學生、家長已知背景／歷史與明示的權重條件決定多結果，並由既有第17-B的seed固定、可重讀及稽核。**不能把`variants`視為重複事件，也不能在驗證工具中強制每個選項只有唯一確定結果。** 多結果的因果必須真正不同，單純換措辭不得冒充兩種不同後果。
- 本工具只讀，不改正式事件引擎、不製作新人物、不替玩家抽事件、不改N1～N8、K倍率、每日上限、年資難度、存檔或部署規則。試產後才評估是否用Codex**以固定規格批次寫草稿**，不允許Codex自說自話跳過驗證或大跑三年／30年。
- 使用現有`validateStory()`、`validateEventDefinitions()`及已有的正式資源解析；**不重建一套平行JSON Schema**。工具與第17-D SOP並存。

## 操作方式（ChatGPT 與 Codex 都一樣）

```bash
# 先查三則第17-D代表小樣，可重現報表
npm run content:audit
node scripts/audit-content.mjs --output work/content-audit.json

# 後續批次提供靜態JSON，不執行上傳內容中的JS
node scripts/audit-content.mjs --input work/content-batch.json --output work/content-batch-report.json

# 18-B補強：新批次對照所有先前已接受事件，舊批次不計入新批產量
node scripts/audit-content.mjs --input work/content-batch.json --baseline work/previous-batches.json --output work/content-batch-report.json

# 嚴格模式：存在格式錯誤、疑似重複或未完成語意審查就以非零狀態結束
node scripts/audit-content.mjs --input work/content-batch.json --strict
```

輸入格式是`{ "records":[{"story":{...},"definition":{...},"editorial":{...},"editorialReview":{...}}] }`，也可直接提供陣列。語意欄位`editorial`記錄`cause`、`teacherResponsibility`、`knowledgeSource`、`distinctiveConsequence`；獨立審查資訊`editorialReview`寫`verdict`、`reviewer`、`rationale`。

1. **格式硬檢**：每則獨立驗證故事分支、四格選項、情緒分類、條件替換、合法場景、數值、選項多結果、歷史代碼，以及事件候選定義和故事ID／版號一致性。保留錯誤訊息與事件ID，**有錯就修該則**。
2. **語意待審標記**：程式不能直接判斷選項「好不好」、責任是否合理，只能要求另填客觀起因、教師責任、資訊來源與實際不同的結果；AI 必須依第17-D SOP明確寫出檢查依據。工具僅確認有審查紀錄，**不宣稱任何AI核准可證明內容完全正確**。
3. **疑似換皮預警**：以不同事件的客觀起因做繁中正規化與字串重疊篩選，列出相似成對ID；AI 再比較起因、教師處理責任、可得資訊、後續因果與跨主題差異。**不以相似分數自動刪故事、不把同故事的兩種結果誤算兩個事件**。字面不同但語義相同仍可能漏抓，需要跨批AI審稿與後續實際遊玩回饋。
4. **數量報告**：固定列出全128主題的`authored`、`structurallyValid`、`reviewed`、`resolverReady`、`catalogueReady`，及距離**20個最低值**還差多少。寫到21、30、40或更多仍全部列入。這些欄位不是玩家當前可抽到的事件數；`publishedInNewCareers: not-assessed`，需另行驗證初始化註冊與實際事件候選才能算正式上架。
5. **相同事件、相同選擇的多結果檢查**：合法`variants`至少兩個、權重正數由原有驗證器處理；額外提示「不同variant的實際後果完全相同」的可疑情形。不同合法後果**不會**被當成重複小事件，不要求每選項固定成功或固定失敗。

## 先試產再量產

先以第17-D現有三則ready事件當正常樣本，額外用測試生成**缺少選項、錯誤主題、版號不匹配、相同客觀起因、相同variant結果、21則以上無上限**等負例。只跑`test/content-audit.test.js`與短程已相關的內容測試，**絕不反覆跑整局三年／30年**。

本階段交付的是**第一版可用檢查器和可觀察測試報告**；它不是AI自動寫作模型，也不能讓Codex在無人檢視下把所有數量自動視為高品質。下一步先以一個T主題20+則做人工智慧撰寫／審查的工作流實驗，量測工具是否真正節省ChatGPT與Codex額度，再決定合理的子批次大小。

## Codex未來可用的交付規則（尚未啟用）

1. 僅依指定的主題、既有第17-D SOP及固定檔案位置撰寫一批**客觀起因真正不同**的小事件，20是最低目標而非限額；不要分配40名學生的強制出場數，不創造未經證實的事實。
2. 每則四個真正有別的選項；至少有自然情緒選項；合理設計可能結果，特別要利用合法`variants`，**同事件同選項不保證同結果**。不建立新的隨機引擎，不改校曆／K／N1～N8與存檔邏輯。
3. 完成後**先跑`npm run content:audit`或`--input`精準檢查**，再交AI從不同角度獨立審查；有缺陷只修該則。不得宣稱執行自己沒有跑過的工具，也不得虛報「已上架」。
4. 交付每主題／事件的草稿與完成統計、錯誤清單、疑似重複候選及必要因果測試。不跑全遊戲模擬，不自行合併main或部署，避免額度無限制消耗。

## 18-B 正式事件量產與品質驗收 SOP（與本工具規範並存）

正式工作順序及審稿責任見 [18B-正式事件量產與品質驗收SOP.md](18B-正式事件量產與品質驗收SOP.md)。先研究並建立事件骨架、先期去重、人物資格與因果設計，再寫正式劇情，最後執行程式與獨立AI語意檢查；不把「20則」當上限。新增 `--baseline` 作跨批疑似重複搜尋的唯讀參考，不增加本批統計，仍須由 AI 查明是否實質換皮。AI 審稿及遊玩體驗分布檢查不由本 CLI 自動證明通過。
