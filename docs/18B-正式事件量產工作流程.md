# 第18-B｜正式事件量產工作流程（試產前定稿）

> 此文件是**量產工作流程**，不是平行事件契約。單篇內容仍以 [17-D 事件內容量產 SOP](17D-事件內容量產SOP.md) 為準；結構檢查以 [18-A 事件量產工具規範](18A-事件量產工具使用規範.md) 與現有引擎為準。第18-B先制定流程、補強工具；**尚未完成單主題20+則正式試產**。

## 不可更動的核心
- 128 個主題，每主題至少 20 則真正不同的小事件；20 是下限而非上限；合理題材更多就繼續增加。不以換姓名、背景、話術或結果變體灌數。
- 同事件、同選項可依人物、歷史、關係與合法權重產生不同**合理**後果；同一事件的 variants 不另計件數。seed、存讀、追溯由原事件引擎負責。
- 不更改 N1～N8、K、每日件數、校曆、資格、曝光、事件引擎、存檔，不新建平行結算系統。
- 不以真實新聞的指控代替遊戲世界中已確認的事實。臺灣校園資料只作題材研究、責任和程序的查核依據。

## 同一批七階段；不是七份獨立任務或七次重複驗收
1. **研究題材**：先定一個 T 主題及正式名稱，蒐集公開的校務制度、一般日常、正向、壓力、荒謬及長期困境的可能起因；區分來源事實、推論與虛構劇情。不強迫每類有固定配額。
2. **骨架登記與先期去重**：寫出候選事件清單，每筆至少具備「客觀起因、導師可處理責任、已知／未知與知情來源、與既有故事的實質差異、可能因果」。先和同主題及跨主題舊事件比對；只有實質不同才進正式撰寫。不為湊到20而保留換皮。
3. **人物資格與因果矩陣**：依合法年級、學籍、接觸時段、人物關係、歷史、教師狀態，決定哪些不同走向合理。結果可以是改善、沒有立即變化、保留疑問或連鎖；不得把未知動機寫成確定事實，也不得硬把同選項變為「固定成功／固定失敗」。不要求每個選項都塞 variants。
4. **寫入既有故事契約**：依17-D完成逐頁臺灣校園用語、四個可實施且策略不同的選項、自然情緒選項、合理替換、圖像場景、候選定義與必要後續，使用穩定 ID 與版本；長短依故事需要，不強制每則一樣長。
5. **精準自動檢查與局部修正**：只驗本批內容與必要的既有引擎相容測試。使用18-A格式檢查、跨批疑似重複提示、同選項多結果等價預警。程式的字串相似分數僅為候選警示，不作語意通過證明。
6. **獨立 AI 審稿**：寫作與審稿分開工作流程；逐則比對17-D內容契約、導師責任、人物資格、台灣制度及程序、四選項差異、合理後果、長期連鎖及非換皮理由。審稿須記錄具體依據、待改項與修正結果；高風險議題另查制度程序。只修有問題的事件，再跑受影響的精準檢查；「有審稿欄位」不等於客觀品質保證。
7. **累積與玩法分布檢查**：加入累積登記簿，持續比較全庫「起因、教師策略、結果型態、日常／正向／負面基調、短／長連鎖、人物角色、場景與時段」。避免幾天連續碰到等價情節、永遠同四種策略、每則同長或只用單一數值結算。不強制各類等量；實際抽取與平衡留第21批再驗。

## 最小批次與完成的定義
- 首次試產：**單一主題至少20個真正不同的小事件**；骨架可先提出20～30以上候選，經去重後繼續補足最低數，不設上限。
- 小批穩定後才視內容品質與實際成本擴大至1～2主題甚至更多；不提前承諾每批固定產量與Codex一定省用量。
- 報告至少分開列出 authored（已寫）、structurallyValid（合法）、reviewed（已有具體AI審稿紀錄）、resolverReady、catalogueReady、publishedInNewCareers（真正驗證上架）。**只有後面經驗證的狀態才可聲稱對應完成，不得把審稿數當作上架數。**
- 不做三年／30年全局模擬，不強制40位學生輪流曝光，不要求使用者逐篇驗收。修改前先留底、精準修正即可。
- GitHub：使用既有PR #59分支完善量產工具與規範；未經授權不合併或部署。試產事件下一批另作獨立變更，不混入本次純流程補強。

## 跨批去重操作（18-A工具補強）
舊批次記錄存為靜態 JSON（陣列或 {records:[...]}），同樣具備 editorial.cause 等欄位；新批次亦用現有輸入格式。

```bash
node scripts/audit-content.mjs --input work/new-batch.json --baseline work/previous-batches.json --output work/new-batch-report.json
```

- `--baseline` 只作**比對背景**，不增加本批 authored、valid、reviewed、已上架等統計。
- 僅列「新批對舊批」和「新批內」疑似重複；舊批彼此的舊問題不應讓這批的嚴格檢查卡死。跨批仍需要AI語意審查，文字比對有漏報及誤報。
- baseline應取**累積所有已接受事件**而非只有上一批；版本與ID保持可追溯。檢查器不會自行搜尋GitHub或自動合併每批記錄，量產者必須明確提供檔案。

## ChatGPT／Codex分工決策
先由 ChatGPT 做單主題的骨架、因果與審稿示範；實測完成率、退稿類型、修改次數、工具與對話成本，再決定是否交給 Codex 接固定規格批次。Codex若使用，只產生指定範圍的內容／精準修正並回報實際執行的檢查，不自行大跑模擬、不自行合併部署。兩種方式用相同結構與品質標準比較。
